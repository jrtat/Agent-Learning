# OpenVking 深入理解

## 序言

> date：2026/11/8

由大肥鱼创作，我负责校对，写给第一次用 OpenViking 的人。

本篇回答，在运行过程中，OpenViking 在用户不知道的地方做了什么？

## 总览

下面 8 件事**全自动**，在 DSH 里看不到任何提示：

| 时机 | 它做了什么 | 
| --- | --- | 
| 1. **会话开始** | 初始化一个 OV 会话 `dsh-<session-id>`；注入画像 `profile.md` + 记忆索引 + 技能清单 | 
| 2. **用户每发一句** | 用用户这句话做语义检索（预算 2000 token，相关度阈值 0.35），命中片段作为**隐藏消息**追加到本轮 | 
| 3. **每轮对话** | 捕获 user / assistant /（默认）工具结果的文本到本地缓冲，**跳过**注入的上下文和系统提示 | 
| 4. **到阈值 / 压缩 / 关会话** | 把整段会话 commit 给服务端 | 
| 5. **commit 之后** | 服务端排队：VLM 抽取 → 决定新建/合并记忆 → 写 `memories/**` → 更新 `profile.md` 与索引 | 
| 6. **导入资料时** | 后台解析 → 切块 → 生成 L0/L1 摘要（`.abstract.md`/`.overview.md`）→ 向量化 | 
| 7. **写失败时** | 进 pending 队列，后台每 60 秒探测服务并重放，**不丢数据** | 
| 8. **用户误用 URI 时** | 文件工具碰到 `viking://` 会被拦下，并提示改用 OpenViking 工具 | 

## 关于捕获记忆

捕获记忆主要讲的是它怎么「记笔记」：**只记录“人”和“模型”说过的话，不记录“软件塞进来的话”，而且先把笔记攒在本地内存里，等到某个时机再一次性交上去。** 拆成三件事就清楚了。

**捕获什么**：插件挂在 DSH 的事件流上（session/event），用户每发一条消息、模型每回一段，它就把文本内容抄一份，放进 DSH 进程内的一个列表（“本地缓冲”）。

- 这份列表只在内存里，这时还没发给 OpenViking 服务端。

**跳过什么**：凡是“不是人打的”内容，一律不抄。下面用这次对话做对照：

| 会进缓冲（当作对话内容） | 不会进缓冲（软件塞进来的）|
|---|---|
| 用户打的字：比如「我改了上面的一些错误，并添加了第7步」	| 插件自己注入的画像块和召回片段，也就是这次回答最上面那段 `<openviking-context>` |
| 模型的回复文本：包括我现在写的这段解释 |	DSH 注入的时间上下文，比如「Time sampled while preparing turn 6」那一行 |
| 工具调用的返回结果（默认开启，captureToolResults: true） |	系统提示、技能清单、job 通知，以及其它插件注入的内容 |

**为什么必须跳过**：因为不跳会自己污染自己。

> **回声污染**：召回片段是从用户过去的记忆里检索出来的。如果把它也当成「用户说过的话」抄进缓冲，下一次抽取就会把「检索结果」写成「新记忆」。下一轮召回到这条新记忆，再被抄一次……同一句话被反复确认、不断强化，几轮之后库里全是自我复制的回声，真话反而被淹掉。系统提示同理：它每轮都一样，抄进去只占预算、不带来新信息。

## 补充：子 agent

子 agent 是独立会话，主 agent 在 DSH 里可以派子智能体（subagent）去单独干活。
每个 subagent 在 DSH 里就是一个独立的 session，而插件是按 session 工作的：
- 一个 session → 一个 OpenViking 会话（`dsh-<session-id>`）、各自记账、各自提交。


|  |	主会话 |	某个子 agent |
|---|---|---|
| 谁在里面说话	| 用户和主 agent	| 主 agent 派的子 agent，用户看不到它的过程 |
| OpenViking 里的会话 id	| `dsh-<主会话 id>`	| `dsh-<另一个 id>`，Studio 会话页里会多出一条 |
| 提交单元	| 独立提交	| 独立提交 —— 这就是「不会混进主会话的提交」的意思 |
| 记忆落到哪	| `viking://user/<id>/memories/` |	同一个库。提交单元不同，不等于记忆库不同 |

关键要分清提交单元和记忆库：子 agent 的对话是“单独打的一个包”，但它抽出来的记忆仍然写进用户同一个 `memories/`。

所以子 agent 聊出来的结论，用户在主会话里照样能召回——只是 Studio 里用户会看到多出几条不认识的 `dsh-xxx` 会话，那多半就是子 agent 的。

## 补充：remember

OpenViking 插件给 MCP 工具（remember）起的进程是共享的，一个 profile 只有一个，所有会话共用它。

正因为它被共用，它不知道自己此刻在为哪个会话服务——拿不到“当前是哪个 dsh-xxx 在调用我”这个信息。

所以 remember 只能这么实现：在服务端临时开一个短生命周期会话，把用户交给它的内容塞进去，立刻提交、抽取，然后把这个临时会话丢掉。它没法写进用户正在聊的那个会话里。

由此有三个实际后果。

1. 它是插队。自动捕获要攒够 2 万 token 才提交，remember 不等，几秒到一分钟就落盘。所以“我让它记”通常比“它自己记”先出现。

2. 同一件事可能被写两次，但会被合并。它记一次、自动捕获再记一次，抽取时是去更新已有条目，而不是新建重复文件。所以在 Studio 里看到的是某个文件被改写了，而不是多出一个新文件。
  
3. 它看不见前文。它只拿到用户交给它的那段文字，前面聊过什么它不知道。


最后这条最影响用法，落成一句话：说“记住……”的时候，把事实写成一句自包含的话，不要用指代。

| 例子类型 | 例子内容 |
|---|---|
| 正确✅ | 记住：我的 OpenViking 跑在 Docker 里，端口 1933，Studio 入口是 http://127.0.0.1:1933/studio/ |
| 错误❌ | 记住刚才说的那个方案（用 remember 记忆的时候，不知道"刚才"指的是什么） |

总的来说：remember 是一条手动插队的捷径——它另开临时会话立刻提交，看不见前文，最终和自动捕获落进同一个库。
