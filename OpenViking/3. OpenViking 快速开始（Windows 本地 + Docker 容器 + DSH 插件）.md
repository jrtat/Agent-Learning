# OpenViking 快速开始

## 序言

> 写给第一次用 OpenViking 的人。目标是**建立正确的心智模型，了解OpenViking全部主要功能**，并且知道哪些事是它在你背后自动干的。

> date：2026/11/8

### 什么是 OpenViking

一句话来说：**OpenViking 是给 Agent 用的"上下文数据库"，用文件系统的隐喻管理三类东西。**（想看详细介绍，请转到隔壁。）

| 类别 | 存什么 | URI 根 |
| --- | --- | --- |
| 记忆 memory | 你是谁、你的偏好、发生过什么事、定过什么决定 | `viking://user/<你>/memories/` |
| 资料 resource | 你导入的文档、网页、仓库（会被解析、切块、向量化） | `viking://resources/`、`viking://user/<你>/resources/` |
| 技能 skill | 一份 `SKILL.md` 形式的操作说明，任何接进来的 Agent 都能用 | `viking://user/<你>/skills/`、`viking://agent/skills/` |

`viking://` 是**虚拟路径，不是磁盘路径**。它长得像文件夹、能用 `ls`/`tree`/`grep`/`read` 操作，但背后是数据库 + 向量索引。

### 和"提示词 / 向量库"的区别

OpenViking 不是只服务一个 Agent：同一份库，DSH、Claude Code、Codex、OpenViking 自带的 VikingBot 都能接。

OpenViking 不是提示词模板：内容由服务端抽取、去重、合并，会自己长大。

OpenViking 不是单纯的向量库：每个文件除了向量，还有**分层摘要**。
- 目录/文件旁边自动生成 `.abstract.md`（L0，一句话）、`.overview.md`（L1，概览），原文是 L2。
- 检索先命中 L0/L1 定位，再按需读 L2 原文。这就是它能"先给结论、再给原文"的原因，也是它比"整篇塞进上下文"省 token 的原因。

### 记忆的归属范围（peer）

#### OpenViking 的四层身份（Peer在中间）

| 层 |	是什么 | 你的例子 | 能装什么 |
|---|---|---|---|
|Account	|团队或组织，最外层	 | default（默认）|	viking://agent/ 、viking://resources/ 共享资料 |
|User	| 数据的拥有者、鉴权身份	| jrtat（用户 id）	| user/<id>/ 下自己的记忆、资料、技能、会话 |
|Peer |	User 空间里的一个稳定对象，不是独立身份|	graph-rule（示例名） |	peers/<id>/memories/ 、peers/<id>/resources/ |
|Session	|一次对话	| dsh-<session-id>	| 消息与提交记录 |

官方对 peer 的定义就一句：**当前用户空间中的稳定交互对象**，可以代表一个人或另一个 Agent。它不会创建独立用户，也不签发凭据。

#### 三种内容 × 三层空间

|内容类型	| Account 级（共享）	| User 级	| Peer 级 |
|---|---|---|---|
|记忆 memory	| 没有 Account 级路径 |	viking://user/<id>/memories/ （self）|	viking://user/<id>/peers/<peer_id>/memories/ （peer）|
|资料 resource |	viking://resources/	| viking://user/<id>/resources/ |	viking://user/<id>/peers/<peer_id>/resources/ |
|技能 skill	| viking://agent/skills/ |	viking://user/<id>/skills/| 	没有 peer 级路径 |

> 隐藏的坑：memories/skills/ 是**记忆的一种类型**（“技能执行经验”），和 viking://user/<你>/skills/（SKILL.md 技能包）是两码事。

#### peer 的两个角色

|角色	| 谁在设置	| 作用 |
|---|---|---|
|记忆归着点 | 会话里的 peer_id，memory_policy.peer.enabled / memory_policy.self.enabled |	会话抽取的记忆，写进 self 还是某个 peer |
|访问范围	| 请求里的 actor_peer_id	| 收窄“本次请求能看到哪些 peer 的内容” |

peer 不是权限边界。官方明说：actor peer 只限制当前用户下的 peer 集合，你自己的 self 记忆、自己的资料、以及有权访问的共享资料照旧可见；而且持有完整 User Key 的客户端可以改变甚至省略这个范围。总的来说，peer 是**「组织」工具**，不是**「安全」工具**。想隔离敏感数据，要用不同的 User 身份或 ACL。

#### DSH 中的 peer

| 维度 | 原生语义 | DSH 插件的用法 |
| --- | --- | --- |
| peer 代表 | 对话的另一方：一个人或另一个 Agent | 一个工作目录或项目 |
| 谁决定 | 你自己显式指定 `peer_id` | 插件按 git `origin` 或 cwd 自动推导（`peerSource`） |
| 记忆按什么分 | 关于谁（self 与 peer） | 在哪个项目里说的 |
| 典型价值 | 给不同对象维护不同偏好（如“评审建议按问题、影响、建议三列”） | 防止 A 项目的记忆串到 B 项目 |

一条记忆写在哪个空间，取决于**你当时在哪个工作目录**：

- 目录是 git 仓库 → 用仓库 `origin` 归一化成 peer（同一个仓库的 clone / worktree / 子目录共用一个）；

- 目录不是 git 仓库，也没配置 → **不发送 peer，记忆落到用户级空间** `viking://user/jrtat/memories`（全局共享）。

如果想手动让某个目录有独立记忆，在它下面放一个 `.openviking/config.json`：

```json
{ "version": 1, "peer": { "id": "一个独立的名字" } }
```

关于peer_id的一些补充：
- id 用 ASCII 单段、别带 /；
- 指定的peer只对新会话生效；
- 同名即同一抽屉（peer），换机器接着用就延续上下文。

### 三个入口（按场景选）

| 入口 | 适合做什么 | 代价 |
| --- | --- | --- |
| **DSH 对话**（插件已接管） | 日常：让它记、让它查、让它带 URI 回答。零操作 | 看不到中间过程，需要去 Studio 核对 |
| **Studio**（浏览器） | 看：库长什么样、任务跑完没有、原文是什么、记忆被抽成什么 | 要手动开，鉴权要点一次 |
| **ov CLI**（需安装） | 批量：脚本化导入、定时同步、CI 里用 | `npm i -g @openviking/cli` 并配连接 |

三者读写的是**同一份库**。日常只用 DSH；想"看见"就用 Studio；要自动化才装 CLI。

## 体验路线

### 第 0 步：把 Studio 连上

> Studio 是服务端自带的静态前端，走同一套 HTTP API，所以它看到的就是 Agent 看到的，没有"另一份数据"。

打开 <http://127.0.0.1:1933/studio/>  → 选**开源服务**  → 地址 `http://127.0.0.1:1933` → 身份页填**用户 API Key**  → 验证连接  → 进入。

**用户 API Key** 就是 `%USERPROFILE%\.openviking\ovcli.conf` 里 `api_key` 的**整串原值**
- 形如 `ZGVmYXVsdA.anJ0YXQ.xxx`，`.` 分隔的是 account、user、凭据哈希。

若被要求 Root/Admin Key，那是 `ov.conf` 里的 `root_api_key`，日常浏览不需要。

进去后左侧导航：**文件系统、检索、任务中心、会话、技能、监控**。 先点「文件系统」，展开 `user → jrtat（用户名） → memories`。
