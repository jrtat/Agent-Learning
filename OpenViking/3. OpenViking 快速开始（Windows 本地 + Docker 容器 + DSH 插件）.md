# OpenViking 快速开始

## 序言

> date：2026/11/8

由大肥鱼创作，我负责校对，写给第一次用 OpenViking 的人。

目标是**建立正确的心智模型，了解 OpenViking 全部主要功能**，并且知道哪些事是它自动干的。

### 什么是 OpenViking

一句话来说：**OpenViking 是给 Agent 用的"上下文数据库"，用文件系统的隐喻管理三类东西。**

| 类别 | 存什么 | URI 根（未展开 peer） |
| --- | --- | --- |
| 记忆 memory | 用户是谁、用户的偏好、发生过什么事、定过什么决定 | `viking://user/<用户 ID>/memories/` |
| 资料 resource | 用户导入的文档、网页、仓库（会被解析、切块、向量化） | `viking://resources/`、`viking://user/<用户 ID>/resources/` |
| 技能 skill | 一份 `SKILL.md` 形式的操作说明，任何接进来的 Agent 都能用 | `viking://user/<用户 ID>/skills/`、`viking://agent/skills/` |

`viking://` 是**虚拟路径，不是磁盘路径**。它长得像文件夹、能用 `ls`/`tree`/`grep`/`read` 操作，但背后是数据库 + 向量索引。

### OpenViking 的空间结构

#### 四层身份（Peer 在中间）

| 层 |	是什么 | 例子 | 能装什么 |
|---|---|---|---|
| Account	|团队或组织，最外层	 | default（默认）|	`viking://agent/` 、`viking://resources/` 共享资料 |
| User	| 数据的拥有者、鉴权身份	| jrtat（用户 ID）	| `viking://user/<id>/` 下自己的记忆、资料、技能、会话 |
| Peer |	User 空间里的一个稳定对象，不是独立身份|	graph-rule（示例名） |	`viking://user/<id>/peers/<peer_id>/memories/` 、`viking://user/<id>/peers/<peer_id>/resources/` |
| Session	|一次对话	| `dsh-<session-id>`	| 消息与提交记录 |

官方对 peer 的定义就一句：**当前用户空间中的稳定交互对象**，可以代表一个人或另一个 Agent。它不会创建独立用户，也不签发凭据。

#### 三种内容 × 三层空间

| 内容类型	| Account 级（共享）	| User 级	| Peer 级 |
|---|---|---|---|
| 记忆 memory	| 没有 Account 级路径 |	`viking://user/<id>/memories/` （self）|	`viking://user/<id>/peers/<peer_id>/memories/` （peer）|
| 资料 resource |	`viking://resources/`	| `viking://user/<id>/resources/` |	`viking://user/<id>/peers/<peer_id>/resources/` |
| 技能 skill	| `viking://agent/skills/` |	`viking://user/<id>/skills/` | 	没有 peer 级路径 |

> 隐藏的坑：`memories/skills/` 是**记忆的一种类型**（“技能执行经验”），和 `viking://user/<用户 ID>/skills/`（`SKILL.md` 技能包）是两码事。

#### peer 的两个角色

|角色	| 谁在设置	| 作用 |
|---|---|---|
|记忆归着点 | 会话里的 `peer_id`，`memory_policy.peer.enabled` / `memory_policy.self.enabled` |	会话抽取的记忆，写进 self 还是某个 peer |
|访问范围	| 请求里的 `actor_peer_id`	| 收窄“本次请求能看到哪些 peer 的内容” |

peer 不是权限边界。官方明说：actor peer 只限制当前用户下的 peer 集合，用户自己的 self 记忆、自己的资料、以及有权访问的共享资料照旧可见；而且持有完整 User Key 的客户端可以改变甚至省略这个范围。总的来说，peer 是**「组织」工具**，不是**「安全」工具**。想隔离敏感数据，要用不同的 User 身份或 ACL。

#### DSH 中的 peer

| 维度 | 原生语义 | DSH 插件的用法 |
| --- | --- | --- |
| peer 代表 | 对话的另一方：一个人或另一个 Agent | 一个工作目录或项目 |
| 谁决定 | 用户显式指定 `peer_id` | 插件按 git `origin` 或 cwd 自动推导（`peerSource`） |
| 记忆按什么分 | 关于谁（self 与 peer） | 在哪个项目里说的 |
| 典型价值 | 给不同对象维护不同偏好（如“评审建议按问题、影响、建议三列”） | 防止 A 项目的记忆串到 B 项目 |

一条记忆写在哪个空间，取决于**用户当时在哪个工作目录**：

- 目录是 git 仓库 → 用仓库 `origin` 归一化成 peer（同一个仓库的 clone / worktree / 子目录共用一个）；

- 目录不是 git 仓库，也没配置 → **不发送 peer，记忆落到用户级空间** `viking://user/jrtat/memories`（全局共享）。

如果想手动让某个目录有独立记忆，在它下面放一个 `.openviking/config.json`：

```json
{ "version": 1, "peer": { "id": "一个独立的名字" } }
```

关于 `peer_id` 的一些补充：
- id 用 ASCII 单段、别带 `/`；
- 指定的 peer 只对新会话生效；
- 同名即同一抽屉（peer），换机器接着用就延续上下文。

## 体验路线

### 第 0 步：把 Studio 连上

> Studio 是服务端自带的静态前端，走同一套 HTTP API，所以它看到的就是 Agent 看到的，没有"另一份数据"。

打开 <http://127.0.0.1:1933/studio/>  → 选**开源服务**  → 地址 `http://127.0.0.1:1933` → 身份页填**用户 API Key**  → 验证连接  → 进入。

**用户 API Key** 就是 `%USERPROFILE%\.openviking\ovcli.conf` 里 `api_key` 的**整串原值**
- 形如 `ZGVmYXVsdA.anJ0YXQ.xxx`，`.` 分隔的是 account、user、凭据哈希。

若被要求 Root/Admin Key，那是 `ov.conf` 里的 `root_api_key`，日常浏览不需要。

进去后左侧导航：**文件系统、检索、任务中心、会话、技能、监控**。 先点「文件系统」，展开 `user → jrtat（用户 ID） → memories`。

### 第 1 步：验证自动召回

在 DSH 里问一件**只有早期会话才知道**的事，比如：

> 我某某项目的前端最后选的是什么方案？为什么放弃另外两个？

**应该看到**：

- 它答得出（当时对话的内容），而不是反问用户要背景。

**去哪核对**：

- Studio → `user/jrtat/memories/preferences/`、`entities/` 里对应的 md。

**背后**：

- 这次会话一开始，插件就把用户的画像块（`<user-profile>` + `<available-memories>` 索引 + 技能清单）注入进去了；

- 用户每发一句话，它还会拿这句话做一次语义检索，把命中片段作为一条**隐藏的插件消息**追加到同一轮里。

- 用户看到的"它记得"，其实是这两处注入的结果。

### 第 2 步：写入 + 抽取

用自然语言让 DSH 记住某件事，比如

> 记住：我的 OpenViking 服务在 Docker 里跑，端口 1933，Studio 入口是 http://127.0.0.1:1933/studio/ ，embedding 用 Cloudflare bge-m3。

**应该看到**：

- 它回一句"已记录"，然后**不要期待立刻**出现——抽取是异步的，通常 10 秒到 1 分钟。

**去哪看**：

- Studio → 文件系统 → `user/jrtat/memories/`，刷新；

- 可能出现在 `entities/软件部署/openviking.md`（被合并进已有条目）或 `preferences/` 下新文件。

**背后**：

- `remember` 只是把用户交给它的那段文字投给服务端，真正的落盘是后台抽取任务干的：VLM 读这段内容 → 决定新建还是合并 → 写 md → 更新索引和 `profile.md`。

**重要**：

- 所以"记了但没看到"通常不是失败，是还没抽完。

- 也可以**直接改文件**：在 Studio 里打开 `profile.md` 手写一行，下次会话就会原样注入——这是最可控的"钉住一个事实"的办法。

### 第 3 步：喂资料（resource）

用自然语言的方式让 DSH 把内容记录到资料中：

| 来源 | 怎么提问 |
| --- | --- |
| 本地文件 | 「把 `C:\...\手册.md` 收进 OpenViking，放到 `viking://resources/手册`，处理完告诉我」 |
| 网页 | 「把这个网页收进来：https://docs.openviking.ai/zh/getting-started/09-memory」 |
| Git 仓库 | 「把 https://github.com/volcengine/OpenViking 的文档收进来」 |

**去哪看进度**：

- Studio → **任务中心**，能看到"解析 → 语义处理 → 嵌入向量"三个阶段；`已完成` 才算好。

**验收三连**（用 DSH 说，或 Studio 检索页做）：

1. 「列一下 `viking://resources/手册` 里有什么」→ 应看到目录树；

2. 「在 `viking://resources/手册` 里找关于 XX 的内容」→ 应返回带 URI 的命中；
  
3. 「读一下 `<URI>` 原文」→ 应看到原文，而不是摘要。

**背后**：

- 导入是**后台队列任务**，不是同步的。

- 服务端会把文件解析成文本、切块、生成 L0/L1 摘要、算向量，并在目录旁写 `.abstract.md`/`.overview.md`。

- 用户只看到"已开始处理"，剩下的在用户不知道的地方跑完。

### 第 4 步：溯源

> 只依据 `viking://resources/手册` 里的资料回答：xxxxxx（一个具体的问题）。

**应该看到**：

- 结论 + URI 列表；缺依据时它承认。

**核对**：

- 把 URI 粘到 Studio 文件系统里打开，逐条比。这就是"能不能追到原文出处"的实操方式。

**背后**：

- 检索命中的是**摘要层**（L0/L1），所以它常常先"知道有这份资料"，再调 `read` 取原文；

- 如果它没给 URI，说明它没走到 `read`，可以直接要求"先把原文读出来再答"。

### 第 5 步：把一套流程变成技能（skill）

> 把"论文逐段中英对照翻译"的流程写成 OpenViking 技能，名字 `paper-translate`。要包含 STYLE.md 规范、术语表维护、每段交付格式。

**去哪看**：

- Studio → **技能**，或 DSH 里「列一下我的技能」。

**应该看到**：

- `viking://user/<用户 ID>/skills/paper-translate/SKILL.md`，之后**任何**接入同一账号的 harness，会话开头都会在技能清单里看到它，需要时自动读。

**背后**：

- `add_skill` 把整份 `SKILL.md` 文本装成"数据"，不是装成代码插件；

- 它只影响 Agent 的行为指引，不会执行任何程序。技能清单每会话注入一次，有独立 token 预算（默认 1200），所以描述要写得像"什么任务该用它"。

### 第 6 步：看会话是怎么变成记忆的

**去哪看**：

- Studio → **会话**，找 `dsh-<session-id>`，看消息、看会话提交后记忆的变化。

**重点理解**：

- **只有 commit 了才产生记忆**。commit 的触发点是：累计 token 超过阈值（默认 20000）、DSH 开始压缩上下文、或会话关闭。

- 所以一次很短的对话可能"什么都没沉淀"，这不是 bug。

**背后**：

- 插件在本地缓冲用户、助手、以及（默认）工具结果的文本；到点整段提交；服务端再排队抽取。

### 第 7 步：治理与卫生（按需）

| 想做的事 | 怎么做 | 注意 |
| --- | --- | --- |
| 删一条记忆 | 「把关于 X 的那条记忆删掉」→ 它调 `forget` | **不可逆**，删除前让它先把 URI 念给用户看 |
| 让某目录独立记忆 | 放 `.openviking/config.json` 指定 `peer.id` | 只对新会话生效 |
| 备份 | 复制 `%USERPROFILE%\.openviking\`（尤其 `data\` 和 `ov.conf`） | 无 |
| 导出/迁移 | Studio 顶部的 OVPack 入口；或 `ov` CLI 的导入导出 | 换机器最省事的方式 |
| 多人/多端隔离 | account / user / ACL / 隐私配置 | 单人自用可以先跳过 |


## 目前不具备的能力

以下要升级/额外启动才有：

**VikingBot**（在启动时加 --with-bot 就可启动 VikingBot）：
- OpenViking 自带的对话 Agent，跑在服务端进程里（--with-bot），内置了检索、读取、记忆这套工具，等于「不装任何 harness 也能直接跟这个库聊天」。

**规则 Rule（Beta）**：
- 把规范编译成可检索的规则条目，存在 memories/rules。执行任务前按当前任务内容检索「这次适用哪几条」，带 0.65 的概率阈值。

**Agent 经验 Experience**：
- memories/ 下的 experiences、trajectories、cases、tools 几类，记录「这类任务上次怎么做、哪步踩坑」，配套 search_experience 在执行类任务前先查。

**上下文编译（Compile）**：
- 把源资料编译成产物：LLM Wiki、知识图谱、日报、知识蒸馏、记忆整合。需要 Compile Runtime（执行环境 + 模型）才跑得起来。

**ov CLI**：
- 命令行客户端（npm 包），不是服务端能力。ov add-resource --wait、ov task status、ov find、ov read、ov tree、导入导出都靠它。

| 项目	|  缺了会少什么 | 现在需要吗 |
|---|---|---|
| VikingBot	| Studio 的 VikingBot 页是空的，ov chat 不可用。不影响到 DSH，因为两者读的是同一个库	| 不需要。已有 DSH，能力还更强。它唯一的价值是「验证这个库脱离 DSH 也能独立用」 |
| 规则 Rules（Beta） |	 少了「任务前自动查规则」这一步。现在的 preferences 仍然会被注入，只是不判定适用性	| 不急。个人使用 preference 够用；Rules 是给团队做硬约束的（比如「删文件前必须确认」）|
| Agent 经验 Experience	| 少一层「复盘复用」。事件、偏好这些普通记忆照常工作 |	暂时不需要。当需要反复做同类实验或部署时，它才会有明显价值 |
| 上下文编译 Compile	| 只能「查」不能「生成成篇的东西」。但注意：智能体可以自己读资料再写，不一定非得走 Compile	| 不需要。目前产出主要靠对话生成，Compile 是给「定期自动出报告」这类场景的 |
| ov CLI	| 只能用 Studio 和对话，没法脚本化、定时、批量	| 可选但值得装。成本约一分钟，ovcli.conf 已经配好，装完 ov health 直接通 |
