# OpenViking 快速开始

## 序言

> date：2026/11/8

由大肥鱼创作，我负责校对，写给第一次用 OpenViking 的人。

目标是**建立正确的心智模型，了解 OpenViking 全部主要功能**，并且知道哪些事是它在你背后自动干的。

### 什么是 OpenViking

一句话来说：**OpenViking 是给 Agent 用的"上下文数据库"，用文件系统的隐喻管理三类东西。**（想看详细介绍，请转到隔壁。）

| 类别 | 存什么 | URI 根（未展开 peer） |
| --- | --- | --- |
| 记忆 memory | 你是谁、你的偏好、发生过什么事、定过什么决定 | `viking://user/<你>/memories/` |
| 资料 resource | 你导入的文档、网页、仓库（会被解析、切块、向量化） | `viking://resources/`、`viking://user/<你>/resources/` |
| 技能 skill | 一份 `SKILL.md` 形式的操作说明，任何接进来的 Agent 都能用 | `viking://user/<你>/skills/`、`viking://agent/skills/` |

`viking://` 是**虚拟路径，不是磁盘路径**。它长得像文件夹、能用 `ls`/`tree`/`grep`/`read` 操作，但背后是数据库 + 向量索引。

### 和"提示词 / 向量库"的区别

OpenViking 不是只服务一个 Agent：同一份库，DSH、Claude Code、Codex、OpenViking 自带的 VikingBot 都能接。

OpenViking 不是提示词模板：内容由服务端抽取、去重、合并，会自己长大。

OpenViking 不是单纯的向量库：每个文件除了向量，还有**分层摘要**。
- 目录/文件旁边自动生成 `.abstract.md`（L0，一句话）、`.overview.md`（L1，概览），原文是 L2。
- 检索先命中 L0/L1 定位，再按需读 L2 原文。这就是它能"先给结论、再给原文"的原因，也是它比"整篇塞进上下文"省 token 的原因。

### OpenViking 的空间结构

#### 四层身份（Peer 在中间）

| 层 |	是什么 | 你的例子 | 能装什么 |
|---|---|---|---|
| Account	|团队或组织，最外层	 | default（默认）|	`viking://agent/` 、`viking://resources/` 共享资料 |
| User	| 数据的拥有者、鉴权身份	| jrtat（用户 id）	| `viking://user/<id>/` 下自己的记忆、资料、技能、会话 |
| Peer |	User 空间里的一个稳定对象，不是独立身份|	graph-rule（示例名） |	`viking://user/<id>/peers/<id>/memories/` 、`viking://user/<id>/peers/<id>/resources/` |
| Session	|一次对话	| dsh-<session-id>	| 消息与提交记录 |

官方对 peer 的定义就一句：**当前用户空间中的稳定交互对象**，可以代表一个人或另一个 Agent。它不会创建独立用户，也不签发凭据。

#### 三种内容 × 三层空间

| 内容类型	| Account 级（共享）	| User 级	| Peer 级 |
|---|---|---|---|
| 记忆 memory	| 没有 Account 级路径 |	`viking://user/<id>/memories/` （self）|	`viking://user/<id>/peers/<peer_id>/memories/` （peer）|
| 资料 resource |	`viking://resources/`	| `viking://user/<id>/resources/` |	`viking://user/<id>/peers/<peer_id>/resources/` |
| 技能 skill	| `viking://agent/skills/` |	`viking://user/<id>/skills/` | 	没有 peer 级路径 |

> 隐藏的坑：`memories/skills/` 是**记忆的一种类型**（“技能执行经验”），和 `viking://user/<你>/skills/`（`SKILL.md` 技能包）是两码事。

#### peer 的两个角色

|角色	| 谁在设置	| 作用 |
|---|---|---|
|记忆归着点 | 会话里的 `peer_id`，`memory_policy.peer.enabled` / `memory_policy.self.enabled` |	会话抽取的记忆，写进 self 还是某个 peer |
|访问范围	| 请求里的 `actor_peer_id`	| 收窄“本次请求能看到哪些 peer 的内容” |

peer 不是权限边界。官方明说：actor peer 只限制当前用户下的 peer 集合，你自己的 self 记忆、自己的资料、以及有权访问的共享资料照旧可见；而且持有完整 User Key 的客户端可以改变甚至省略这个范围。总的来说，peer 是**「组织」工具**，不是**「安全」工具**。想隔离敏感数据，要用不同的 User 身份或 ACL。

#### DSH 中的 peer

| 维度 | 原生语义 | DSH 插件的用法 |
| --- | --- | --- |
| peer 代表 | 对话的另一方：一个人或另一个 Agent | 一个工作目录或项目 |
| 谁决定 | 你自己显式指定 `peer_id` | 插件按 git `origin` 或 cwd 自动推导（`peerSource`） |
| 记忆按什么分 | 关于谁（self 与 peer） | 在哪个项目里说的 |
| 典型价值 | 给不同对象维护不同偏好（如“评审建议按问题、影响、建议三列”） | 防止 A 项目的记忆串到 B 项目 |

一条记忆写在哪个空间，取决于**你当时在哪个工作目录**：

- 目录是 git 仓库 → 用仓库 `origin` 归一化成 peer（同一个仓库的 clone / worktree / 子目录共用一个）；

- 目录不是 git 仓库，也没配置 → **不发送 peer，记忆落到用户级空间** `viking://user/jrtat/memories`（全局共享）。

如果想手动让某个目录有独立记忆，在它下面放一个 `.openviking/config.json`：

```json
{ "version": 1, "peer": { "id": "一个独立的名字" } }
```

关于 `peer_id` 的一些补充：
- id 用 ASCII 单段、别带 `/`；
- 指定的peer只对新会话生效；
- 同名即同一抽屉（peer），换机器接着用就延续上下文。

### 三个入口（按场景选）

| 入口 | 适合做什么 | 代价 |
| --- | --- | --- |
| **DSH 对话**（插件已接管） | 日常：让它记、让它查、让它带 URI 回答。零操作 | 看不到中间过程，需要去 Studio 核对 |
| **Studio**（浏览器） | 看：库长什么样、任务跑完没有、原文是什么、记忆被抽成什么 | 要手动开，鉴权要点一次 |
| **ov CLI**（需安装） | 批量：脚本化导入、定时同步、CI 里用 | `npm i -g @openviking/cli` 并配连接 |

三者读写的是**同一份库**。日常只用 DSH；想"看见"就用 Studio；要自动化才装 CLI。

## 体验路线

### 第 0 步：把 Studio 连上

> Studio 是服务端自带的静态前端，走同一套 HTTP API，所以它看到的就是 Agent 看到的，没有"另一份数据"。

打开 <http://127.0.0.1:1933/studio/>  → 选**开源服务**  → 地址 `http://127.0.0.1:1933` → 身份页填**用户 API Key**  → 验证连接  → 进入。

**用户 API Key** 就是 `%USERPROFILE%\.openviking\ovcli.conf` 里 `api_key` 的**整串原值**
- 形如 `ZGVmYXVsdA.anJ0YXQ.xxx`，`.` 分隔的是 account、user、凭据哈希。

若被要求 Root/Admin Key，那是 `ov.conf` 里的 `root_api_key`，日常浏览不需要。

进去后左侧导航：**文件系统、检索、任务中心、会话、技能、监控**。 先点「文件系统」，展开 `user → jrtat（用户 ID） → memories`。

## OpenViking 在你不知道的地方做了什么

### 总览

下面 8 件事**全自动**，在 DSH 里看不到任何提示：

| 时机 | 它做了什么 | 
| --- | --- | 
| 1. **会话开始** | 初始化一个 OV 会话 `dsh-<session-id>`；注入画像 `profile.md` + 记忆索引 + 技能清单 | 
| 2. **你每发一句** | 用你这句话做语义检索（预算 2000 token，相关度阈值 0.35），命中片段作为**隐藏消息**追加到本轮 | 
| 3. **每轮对话** | 捕获 user / assistant /（默认）工具结果的文本到本地缓冲，**跳过**注入的上下文和系统提示 | 
| 4. **到阈值 / 压缩 / 关会话** | 把整段会话 commit 给服务端 | 
| 5. **commit 之后** | 服务端排队：VLM 抽取 → 决定新建/合并记忆 → 写 `memories/**` → 更新 `profile.md` 与索引 | 
| 6. **导入资料时** | 后台解析 → 切块 → 生成 L0/L1 摘要（`.abstract.md`/`.overview.md`）→ 向量化 | 
| 7. **写失败时** | 进 pending 队列，后台每 60 秒探测服务并重放，**不丢数据** | 
| 8. **你误用 URI 时** | 文件工具碰到 `viking://` 会被拦下，并提示改用 OpenViking 工具 | 

### 关于追加记忆（第 3 条 - 第 7 条）

追加记忆主要讲的是它怎么“记笔记”：**只记录“人”和“模型”说过的话，不记录“软件塞进来的话”，而且先把笔记攒在本地内存里，等到某个时机再一次性交上去。** 拆成三件事就清楚了。

**捕获什么**：插件挂在 DSH 的事件流上（session/event），你每发一条消息、模型每回一段，它就把文本内容抄一份，放进 DSH 进程内的一个列表（“本地缓冲”）。

- 这份列表只在内存里，这时还没发给 OpenViking 服务端。

**跳过什么**：凡是“不是人打的”内容，一律不抄。下面用这次对话做对照：

| 会进缓冲（当作对话内容） | 不会进缓冲（软件塞进来的）|
|---|---|
| 你打的字：比如「我改了上面的一些错误，并添加了第7步」	| 插件自己注入的画像块和召回片段，也就是这次回答最上面那段 <openviking-context> |
| 模型的回复文本：包括我现在写的这段解释 |	DSH 注入的时间上下文，比如「Time sampled while preparing turn 6」那一行 |
| 工具调用的返回结果（默认开启，captureToolResults: true） |	系统提示、技能清单、job 通知，以及其它插件注入的内容 |

**为什么必须跳过**：因为不跳会自己污染自己。

> **回声污染**：召回片段是从你过去的记忆里检索出来的。如果把它也当成「用户说过的话」抄进缓冲，下一次抽取就会把「检索结果」写成「新记忆」。下一轮召回到这条新记忆，再被抄一次……同一句话被反复确认、不断强化，几轮之后库里全是自我复制的回声，真话反而被淹掉。系统提示同理：它每轮都一样，抄进去只占预算、不带来新信息。

### 补充：子 agent

子 agent 是独立会话，主 agent在 DSH 里可以派子智能体（subagent）去单独干活。
每个 subagent 在 DSH 里就是一个独立的 session，而插件是按 session 工作的：
- 一个 session → 一个 OpenViking 会话（dsh-<session-id>）、各自记账、各自提交。


|  |	主会话 |	某个子 agent |
|---|---|---|
| 谁在里面说话	| 用户和主 agent	| 主 agent 派的子 agent，用户看不到它的过程 |
| OpenViking 里的会话 id	| `dsh-<主会话 id>`	| `dsh-<另一个 id>`，Studio 会话页里会多出一条 |
| 提交单元	| 独立提交	| 独立提交 —— 这就是「不会混进主会话的提交」的意思 |
| 记忆落到哪	| `viking://user/<id>/memories/ |	同一个库。提交单元不同，不等于记忆库不同 |

关键要分清提交单元和记忆库：子 agent 的对话是“单独打的一个包”，但它抽出来的记忆仍然写进你同一个 `memories/`。

所以子 agent 聊出来的结论，你在主会话里照样能召回——只是 Studio 里你会看到多出几条不认识的 `dsh-xxx` 会话，那多半就是子 agent 的。

### 补充：remember

OpneViking 插件给 MCP 工具（remember）起的进程是共享的，一个 profile 只有一个，所有会话共用它。

正因为它被共用，它不知道自己此刻在为哪个会话服务——拿不到“当前是哪个 dsh-xxx 在调用我”这个信息。

所以 remember 只能这么实现：在服务端临时开一个短生命周期会话，把你交给它的内容塞进去，立刻提交、抽取，然后把这个临时会话丢掉。它没法写进你正在聊的那个会话里。

由此有三个实际后果。

1. 它是插队。自动捕获要攒够 2 万 token 才提交，remember 不等，几秒到一分钟就落盘。所以“我让它记”通常比“它自己记”先出现。

2. 同一件事可能被写两次，但会被合并。它记一次、自动捕获再记一次，抽取时是去更新已有条目，而不是新建重复文件。所以在 Studio 里看到的是某个文件被改写了，而不是多出一个新文件。
  
3. 它看不见前文。它只拿到你交给它的那段文字，前面聊过什么它不知道。


最后这条最影响用法，落成一句话：说“记住……”的时候，把事实写成一句自包含的话，不要用指代。

| 例子类型 | 例子内容 |
|---|---|
| 正确✅ | 记住：我的 OpenViking 跑在 Docker 里，端口 1933，Studio 入口是 http://127.0.0.1:1933/studio/ |
| 错误❌ | 记住刚才说的那个方案（第二句没有“刚才”，抽出来的记忆会是残缺的。） |

总的来说：remember 是一条手动插队的捷径——它另开临时会话立刻提交，看不见前文，最终和自动捕获落进同一个库。
