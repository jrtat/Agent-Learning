# OpenViking 记忆系统说明

> OpenViking 是一个面向 AI Agent 的**上下文数据库（Context Database）** 或 **记忆文件系统**。
> 它不只是把聊天记录转成向量，而是尝试将记忆、资源和技能组织成可检索、可导航、可管理的层次化上下文空间。
> date: 2026/10/16

# 序言

现在关于Agent记忆，各家都有各家的讨论，OpenViking是字节旗下火山引擎推出的开源方案，是“**文件系统即记忆**”的典型代表。下面是我和大肥鱼激情交互后，经大肥鱼总结，我简单校对后得到的文档。



## 一、系统定位

传统的向量记忆系统通常采用如下流程：

```text
聊天记录
  ↓
切分文本
  ↓
生成向量
  ↓
相似度搜索
  ↓
拼接若干文本片段
```

这种方式虽然简单，但存在一些问题：

- 文本片段之间缺乏层次关系；
- 找到的内容可能只是语义相似，并不一定真正相关；
- 重要事实、临时事件、项目资料（这些内容的来源、性质不同）容易混在一起；
- 召回结果容易碎片化或过量；
- 记忆难以修改、删除、审计和迁移（可管理性差）。

OpenViking 的目标是解决更完整的上下文管理问题：

> 让 Agent 能够长期**保存**、**组织**、**检索**和**治理**上下文，而不是简单地保存聊天历史。

# 二、架构层面：OpenViking 如何解决记忆问题

## 2.1 核心理念：文件系统范式

OpenViking 使用类似**文件系统**的**虚拟 URI** 组织内容，例如：

```text
viking://user/<user_id>/memories/entities/软件部署/openviking.md
```

该URI不一定对应宿主机上的普通文件，而是 OpenViking 内部的虚拟资源路径。

它具有文件系统的典型特征：

- 有**目录**和**文件**；
- 有明确的**父子关系**；
- 可以**浏览目录**；
- 可以**用路径表达检索范围**；
- 可以**读取具体文件**；
- 可以**在高层目录保存摘要**；
- 可以**从粗粒度信息逐步展开到细粒度内容**。

例如：

```text
viking://user/jrtat/
├── memories/
│   ├── entities/
│   │   └── 软件部署/
│   │       └── openviking.md
│   └── events/
│       └── 2026/
│           └── 10/
│               └── 16/
│                   └── 记忆抽取全链路验证成功.md
├── resources/
└── skills/
```

这样，系统既可以把“软件部署”作为整体理解，也可以继续深入读取具体的一条记忆。

## 2.2 分层上下文检索

OpenViking 的检索可以概括为：

```
用户查询
  ↓
“查询意图”分析
  ↓
定位相关“目录、实体或资源”
  ↓
“语义检索”和“关键词检索”
  ↓
“按层次逐步展开”
  ↓
“组装”有限长度的“上下文”
```

这与单纯的向量数据库不同：
- **向量**负责找到*语义上相近的内容*；
- **文件系统层次**帮助系统*理解内容属于哪个范围*；
- **摘要**帮助系统*先判断目录是否相关*；
- **读取操作**负责*在需要时展开完整内容*。

因此，OpenViking 更像是：

> 结构化目录 + 语义索引 + 上下文组装系统。

从某种意义上来说，目录就是树，因此可以认为OpenViking是一个树状结构的存储系统。

## 2.3 内部架构

可以从五个层次（或者说角度）理解 OpenViking。

### 第一层：数据接入层

数据来源包括：

- Agent 与用户的对话；
- 显式保存的记忆；
- 本地文件；
- Git 仓库；
- 网页和在线文档；
- Agent Skill；
- 其他外部资源。

在 DSH 中，系统会对对话进行分析，提取其中**具有长期价值的信息**，例如：

- 用户事实；
- 用户偏好；
- 项目决策；
- 部署配置；
- 失败经验；
- 重要事件；
- 可复用的操作经验。

### 第二层：语义处理层

OpenViking 通常需要两类模型能力。

#### Embedding 模型

Embedding模型负责将文本转换为向量，用于相似度检索。当前部署使用：

它主要解决：

> **哪些内容在语义上与当前查询相近**？

#### VLM / LLM模型

VLM 或 LLM 负责更复杂的语义处理，例如：

- **从对话中抽取长期记忆**；
- **生成目录和文件摘要**；
- **分析查询意图**；
- **组织上下文**；
- **对导入资源进行语义理解**。

### 第三层：分层存储层

OpenViking 将数据组织为不同类型和层次。

#### Memories：长期记忆

适合保存：

- 用户身份；
- 用户偏好；
- 项目约定；
- 稳定的环境配置；
- 重要历史决策；
- 失败教训。

#### Resources：外部资源

适合保存：

- 项目文档；
- Git 仓库；
- 网页；
- PDF；
- 产品手册；
- 技术规范。

#### Skills：可复用技能

适合保存：

- 部署流程；
- 故障排查流程；
- 操作规范；
- 可重复执行的任务步骤。

#### Events：时间事件

按时间记录某次发生的事情，例如某次部署、故障或验证：

```text
memories/events/2026/10/16/...
```

#### Entities：实体信息

围绕某个实体长期积累信息，例如：

```text
memories/entities/软件部署/openviking.md
```

其中：

- Events 体现“某天发生了什么”；
- Entities 体现“关于某个对象，长期积累了什么”。

### 第四层：索引与检索层

OpenViking 的检索不只有**向量搜索**，还可能结合：

- **语义搜索**；
- **关键词搜索**；
- **URI 和目录浏览**；
- **文件读取**；
- **目录摘要**；
- **按层次递归展开**；
- **记忆、资源和技能的分类检索**。

### 第五层：服务与客户端层

当前部署可以抽象为：

```text
DSH
 └── OpenViking Memory Plugin
      └── OpenViking Client/MCP
           └── OpenViking Server
                ├── 数据存储
                ├── 向量索引
                ├── Embedding 服务
                └── VLM/LLM 服务
```

当前服务端运行在 Docker 容器中：

```text
容器名：openviking
端口：1933
```

DSH 通过客户端配置和用户密钥访问 OpenViking。
