OpenViking 的配置可以分为三类：

1. 服务端配置；
2. 客户端和身份配置；
3. DSH 集成层配置。

## 一、服务端配置

服务端配置通常位于 `ov.conf` 中。当前 Docker 部署将宿主机目录挂载到容器内：

```text
/app/.openviking
```

因此，配置和数据不会随着容器删除而自动消失。

### Server 配置

主要控制：

- 监听地址；
- 服务端口；
- root 管理密钥；
- 外部访问范围；
- 服务运行模式。

当前部署使用：

```text
host: 0.0.0.0
port: 1933
```

注意事项：

- `0.0.0.0` 方便容器和其他设备访问；
- 必须保护 root key；
- 不建议把管理端口直接暴露到公网；
- root key 不应作为普通数据访问 key 使用。

### Storage 配置

控制数据保存位置和存储实现，通常包括：

- 本地存储路径；
- 向量数据库或向量索引配置；
- 数据持久化位置；
- 索引相关参数。

这部分决定了数据是否持久化，以及查询规模和性能如何。

当前使用本地存储方案，数据目录通过 Docker volume 挂载到宿主机。删除容器不会自动删除数据，但仍建议定期备份整个 `.openviking` 数据目录。

### Embedding 配置

主要配置：

- provider；
- 模型名称；
- API 地址；
- API key；
- 向量维度；
- 超时和重试参数。

当前配置：

```text
模型：@cf/baai/bge-m3
维度：1024
```

切换 Embedding 模型时，需要重点关注向量维度。例如，旧索引是 1024 维，新模型是 1536 维时，旧向量和新向量通常不能直接混用，可能需要重建索引或迁移数据。

同时还需要评估：

- 中文、英文和代码的检索效果；
- API 成本；
- 响应延迟；
- 数据是否需要重新嵌入。

### VLM/LLM 配置

主要配置：

- provider；
- `api_base`；
- API key；
- model；
- timeout；
- temperature；
- max retries；
- 工具调用或函数调用能力。

当前有效配置方向：

```text
provider: volcengine
api_base: https://ark.cn-beijing.volces.com/api/plan/v3
model: deepseek-v4.1-flash
```

需要注意套餐和端点的对应关系：

| 类型 | API 端点示例 |
|---|---|
| Agent Plan | `/api/plan/v3` |
| Coding Plan | `/api/coding/v3` |
| 按量付费 | `/api/v3` |

不能只更换模型名而保留不匹配的 API 端点。

记忆抽取也不应只测试简单请求，例如返回 `OK`。应该使用真实长对话进行验证，因为真实抽取通常涉及：

- 更长的输入；
- 工具调用；
- 结构化输出；
- 多轮推理；
- 更复杂的上下文。

## 3.2 客户端配置

客户端配置通常位于 `ovcli.conf`，主要负责：

- OpenViking 服务地址；
- 访问密钥；
- 当前用户身份；
- 客户端请求参数。

典型配置关系：

```text
url: http://localhost:1933
api_key: user key
```

### Root key 与 user key

| 密钥类型 | 主要用途 |
|---|---|
| root key | 创建用户、管理账号、修改服务配置、查看系统状态 |
| user key | 读写该用户自己的记忆和资源 |

root key 不是用于普通数据读写的万能密钥。在当前部署中，使用 root key 访问用户记忆接口会返回 403，这是权限隔离的一部分。

## 3.3 用户和账号配置

OpenViking 具有账号和用户隔离概念。

当前使用的是测试用户：

```text
user/jrtat
```

对应数据路径类似于：

```text
viking://user/jrtat/memories/
```

切换到正式用户通常需要：

1. 在 Web Studio 或管理接口创建用户；
2. 获取新的 user key；
3. 修改 `ovcli.conf`；
4. 重启或重建 DSH 会话；
5. 验证是否读取到正确的数据。

换 user_id 不等于给原用户改名，而是切换到另一套记忆空间。旧数据不会自动迁移到新用户。

## 3.4 DSH 集成层配置

DSH 集成层主要决定：

- 是否自动召回记忆；
- 召回哪些类别；
- 每次召回的 token 上限；
- 是否保存会话；
- 是否进行会话后的记忆抽取；
- 是否限制在当前项目或当前用户范围；
- 是否加载技能；
- 是否将资源和记忆一起参与检索。

可以这样区分：

```text
OpenViking 服务端：
数据怎么存、怎么索引、由哪个模型处理

DSH 集成层：
什么时候召回、召回什么、注入多少、何时写入
```

# 五、针对当前部署的治理建议

## 第一阶段：从测试身份切换到正式身份

当前数据位于：

```text
user/jrtat
```

建议确认：

- 该用户是否只是测试用户；
- 是否需要创建正式用户；
- 测试记忆是否需要迁移；
- 测试数据是否应该保留为独立空间。

不要简单地把测试用户当成正式用户继续使用，否则测试数据、调试信息和正式记忆容易混在一起。

## 第二阶段：整理现有记忆

重点检查：

```text
memories/entities/软件部署/
memories/events/2026/10/16/
```

并将内容区分为：

- 当前有效配置；
- 已废弃配置；
- 历史故障；
- 部署经验；
- 敏感信息。

尤其要确保历史模型端点不会被误认为当前配置。

## 第三阶段：删除或轮换敏感信息

历史对话中曾出现过 API key 和 Cloudflare token，应优先：

1. 轮换这些密钥；
2. 检查记忆内容；
3. 删除明文凭据；
4. 使用配置文件、环境变量或密钥管理器保存新凭据。

## 第四阶段：建立备份策略

建议至少保留：

```text
每日或每周数据目录备份
配置文件版本记录
重要记忆导出
Docker 部署命令
用户身份和权限清单
```

并定期验证恢复流程。

# 六、总结

OpenViking 的核心价值可以概括为：

> 用文件系统的层次结构组织 Agent 上下文，用模型完成语义理解，用向量和结构化检索提高召回能力，再通过用户和 URI 隔离实现可管理的长期记忆。

对用户而言，最重要的不是无限制地保存更多记忆，而是建立以下三条规则：

1. **区分当前状态、历史事件和外部资源；**
2. **控制用户边界、敏感信息和数据生命周期；**
3. **定期检查、纠错、去重、备份和恢复。**

这样，OpenViking 才能从“能记住东西的数据库”，逐渐成为可靠的 Agent 上下文基础设施。
