# 序

OpenViking 的配置可以分为三类：

1. 服务端配置；
2. 客户端和身份配置；
3. DSH 集成层配置。

## 3.1 服务端配置

服务端配置通常位于 `ov.conf` 中。当前 Docker 部署将宿主机目录挂载到容器内：

```text
/app/.openviking
```

因此，配置和数据不会随着容器删除而自动消失。

### Server 配置

主要控制：

- 监听地址；
- 服务端口；
- root 管理密钥；
- 外部访问范围；
- 服务运行模式。

当前部署使用：

```text
host: 0.0.0.0
port: 1933
```

注意事项：

- `0.0.0.0` 方便容器和其他设备访问；
- 必须保护 root key；
- 不建议把管理端口直接暴露到公网；
- root key 不应作为普通数据访问 key 使用。

### Storage 配置

控制数据保存位置和存储实现，通常包括：

- 本地存储路径；
- 向量数据库或向量索引配置；
- 数据持久化位置；
- 索引相关参数。

这部分决定了数据是否持久化，以及查询规模和性能如何。

当前使用本地存储方案，数据目录通过 Docker volume 挂载到宿主机。删除容器不会自动删除数据，但仍建议定期备份整个 `.openviking` 数据目录。

### Embedding 配置

主要配置：

- provider；
- 模型名称；
- API 地址；
- API key；
- 向量维度；
- 超时和重试参数。

当前配置：

```text
模型：@cf/baai/bge-m3
维度：1024
```

切换 Embedding 模型时，需要重点关注向量维度。例如，旧索引是 1024 维，新模型是 1536 维时，旧向量和新向量通常不能直接混用，可能需要重建索引或迁移数据。

同时还需要评估：

- 中文、英文和代码的检索效果；
- API 成本；
- 响应延迟；
- 数据是否需要重新嵌入。

### VLM/LLM 配置

主要配置：

- provider；
- `api_base`；
- API key；
- model；
- timeout；
- temperature；
- max retries；
- 工具调用或函数调用能力。

当前有效配置方向：

```text
provider: volcengine
api_base: https://ark.cn-beijing.volces.com/api/plan/v3
model: deepseek-v4.1-flash
```

需要注意套餐和端点的对应关系：

| 类型 | API 端点示例 |
|---|---|
| Agent Plan | `/api/plan/v3` |
| Coding Plan | `/api/coding/v3` |
| 按量付费 | `/api/v3` |

不能只更换模型名而保留不匹配的 API 端点。

记忆抽取也不应只测试简单请求，例如返回 `OK`。应该使用真实长对话进行验证，因为真实抽取通常涉及：

- 更长的输入；
- 工具调用；
- 结构化输出；
- 多轮推理；
- 更复杂的上下文。

## 3.2 客户端配置

客户端配置通常位于 `ovcli.conf`，主要负责：

- OpenViking 服务地址；
- 访问密钥；
- 当前用户身份；
- 客户端请求参数。

典型配置关系：

```text
url: http://localhost:1933
api_key: user key
```

### Root key 与 user key

| 密钥类型 | 主要用途 |
|---|---|
| root key | 创建用户、管理账号、修改服务配置、查看系统状态 |
| user key | 读写该用户自己的记忆和资源 |

root key 不是用于普通数据读写的万能密钥。在当前部署中，使用 root key 访问用户记忆接口会返回 403，这是权限隔离的一部分。

## 3.3 用户和账号配置

OpenViking 具有账号和用户隔离概念。

当前使用的是测试用户：

```text
user/jrtat
```

对应数据路径类似于：

```text
viking://user/jrtat/memories/
```

切换到正式用户通常需要：

1. 在 Web Studio 或管理接口创建用户；
2. 获取新的 user key；
3. 修改 `ovcli.conf`；
4. 重启或重建 DSH 会话；
5. 验证是否读取到正确的数据。

换 user_id 不等于给原用户改名，而是切换到另一套记忆空间。旧数据不会自动迁移到新用户。

## 3.4 DSH 集成层配置

DSH 集成层主要决定：

- 是否自动召回记忆；
- 召回哪些类别；
- 每次召回的 token 上限；
- 是否保存会话；
- 是否进行会话后的记忆抽取；
- 是否限制在当前项目或当前用户范围；
- 是否加载技能；
- 是否将资源和记忆一起参与检索。

可以这样区分：

```text
OpenViking 服务端：
数据怎么存、怎么索引、由哪个模型处理

DSH 集成层：
什么时候召回、召回什么、注入多少、何时写入
```

# 四、用户管理视角：记忆增多后如何管理

记忆系统真正困难的地方不是“能不能存”，而是：

> 信息越来越多以后，如何避免噪声、错误、重复和失控。

## 4.1 先管理身份边界

建议至少区分：

- 个人长期记忆；
- 某个项目记忆；
- 某个工作区记忆；
- 测试用户；
- 正式用户；
- 团队共享空间。

可以采用：

```text
测试环境   → test user
个人使用   → personal user
团队共享   → shared account 或独立共享空间
```

当前的 `user/jrtat` 是测试用户，建议不要长期把它当成正式生产身份使用。

## 4.2 建立分类规则

不要把所有内容都保存成“记忆”。可以按用途分类：

| 内容类型 | 适合的 OpenViking 类型 |
|---|---|
| 用户长期偏好、稳定事实 | Memory / Entity |
| 某次部署、故障或验证 | Event |
| 项目文档、Git 仓库、网页 | Resource |
| 可重复执行的操作流程 | Skill 或操作经验 |

一个简单判断标准：

> 以后需要作为事实回忆，用 Memory；以后需要阅读原文，用 Resource；以后需要照着执行，用 Skill 或操作经验。

## 4.3 定期检查目录

建议定期浏览：

```text
viking://user/<user_id>/memories/
viking://user/<user_id>/resources/
viking://user/<user_id>/skills/
```

重点检查：

- 是否存在重复记忆；
- 是否有过时配置；
- 是否把临时调试信息保存成长期事实；
- 是否存在错误提取；
- 是否有敏感信息；
- 是否有无法理解的孤立文件；
- 是否同一项目被多个名称记录。

搜索适合“找东西”，目录浏览适合“做治理”。

## 4.4 及时纠正错误记忆

自动抽取并不总是正确，尤其是在以下情况下：

- 对话中有假设性表达；
- 用户说的是测试数据；
- 同一件事前后发生变化；
- 对话中包含多个候选方案；
- 助手推测被误认为用户事实。

发现错误后，建议：

1. 找到原记忆 URI；
2. 读取完整内容；
3. 修改错误事实；
4. 删除重复或过时记录；
5. 重新检索进行验证。

不要只通过新对话“覆盖”错误内容，因为旧记忆可能仍然会被召回。

## 4.5 区分当前状态和历史事件

例如：

```text
当前状态：
OpenViking 当前使用 deepseek-v4.1-flash，
API 地址为 Agent Plan 端点。

历史事件：
曾经尝试使用其他模型，
因套餐或端点不匹配而失败。
```

二者都可能有价值，但作用不同。建议在记忆中明确标记：

- 当前；
- 已废弃；
- 仅测试；
- 历史；
- 待确认；
- 不要使用。

这样可以避免 Agent 把历史失败配置误认为当前有效配置。

## 4.6 管理重复和冲突

长期使用后可能出现：

```text
事实 A：使用模型 X
事实 B：使用模型 Y
事实 C：正在切换到模型 Z
```

这不一定表示数据错误，但必须表达时间和状态。

推荐写成：

```text
当前配置：
- 模型：Z
- 生效日期：2026-10-16

历史配置：
- X：已弃用，原因是……
- Y：测试过但未投入使用
```

不要让多条互相矛盾的记忆看起来具有同样的有效性。

## 4.7 控制敏感信息

记忆库中应避免保存：

- API key；
- Cloudflare token；
- 数据库密码；
- 私钥；
- Cookie；
- 内网凭据；
- 生产环境访问令牌。

如果密钥已经在对话中出现过，应当：

1. 立即在服务商控制台轮换密钥；
2. 修改 OpenViking 服务端配置；
3. 更新客户端配置；
4. 重启服务；
5. 检查记忆库中是否存在旧密钥；
6. 删除包含旧密钥的记忆；
7. 不要把新密钥再次发送到聊天中。

注意：删除记忆不能替代密钥轮换。密钥一旦暴露，应视为已经失效。

## 4.8 做备份和恢复演练

建议备份：

- OpenViking 数据目录；
- 服务端配置；
- 客户端配置的非敏感部分；
- 用户和账号信息；
- 重要资源索引；
- DSH 插件配置；
- Docker 部署命令和版本信息。

不要把明文密钥直接纳入普通备份。

真正需要备份的是：

```text
配置 + 数据目录 + 用户身份映射 + 密钥管理记录
```

还应定期做一次恢复演练，确认备份确实可以恢复，而不是只确认备份文件存在。

## 4.9 管理模型和成本

OpenViking 的成本可能来自：

- Embedding 调用；
- 记忆抽取；
- 文档解析；
- 摘要生成；
- 查询意图分析；
- 资源重新索引。

建议关注：

- 每次记忆抽取耗时；
- 输入和输出 token；
- 失败和重试次数；
- 单次会话产生多少条记忆；
- 资源重新处理次数；
- 更换向量模型带来的重建成本。

当前环境已经完成一次真实抽取验证：

- 抽取任务约 18.75 秒完成；
- 成功抽取 1 条记忆；
- token 记账正常。

可以将这组数据作为后续配置调整的性能基准。

# 五、针对当前部署的治理建议

## 第一阶段：从测试身份切换到正式身份

当前数据位于：

```text
user/jrtat
```

建议确认：

- 该用户是否只是测试用户；
- 是否需要创建正式用户；
- 测试记忆是否需要迁移；
- 测试数据是否应该保留为独立空间。

不要简单地把测试用户当成正式用户继续使用，否则测试数据、调试信息和正式记忆容易混在一起。

## 第二阶段：整理现有记忆

重点检查：

```text
memories/entities/软件部署/
memories/events/2026/10/16/
```

并将内容区分为：

- 当前有效配置；
- 已废弃配置；
- 历史故障；
- 部署经验；
- 敏感信息。

尤其要确保历史模型端点不会被误认为当前配置。

## 第三阶段：删除或轮换敏感信息

历史对话中曾出现过 API key 和 Cloudflare token，应优先：

1. 轮换这些密钥；
2. 检查记忆内容；
3. 删除明文凭据；
4. 使用配置文件、环境变量或密钥管理器保存新凭据。

## 第四阶段：建立备份策略

建议至少保留：

```text
每日或每周数据目录备份
配置文件版本记录
重要记忆导出
Docker 部署命令
用户身份和权限清单
```

并定期验证恢复流程。

# 六、总结

OpenViking 的核心价值可以概括为：

> 用文件系统的层次结构组织 Agent 上下文，用模型完成语义理解，用向量和结构化检索提高召回能力，再通过用户和 URI 隔离实现可管理的长期记忆。

对用户而言，最重要的不是无限制地保存更多记忆，而是建立以下三条规则：

1. **区分当前状态、历史事件和外部资源；**
2. **控制用户边界、敏感信息和数据生命周期；**
3. **定期检查、纠错、去重、备份和恢复。**

这样，OpenViking 才能从“能记住东西的数据库”，逐渐成为可靠的 Agent 上下文基础设施。
