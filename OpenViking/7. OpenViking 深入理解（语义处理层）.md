# OpenViking 深入理解（语义处理层）

## 序言

> date: 2026/11/8

由大肥鱼创作，我负责校对。

目的是更细致地介绍 OpenViking 的理念、架构、功能和执行流程。

目前计划从五个层次理解 OpenViking 的内部架构，这是第三节：语义处理层。

这一篇讲数据进入 OpenViking 之后，OpenViking 对它做了什么。

## 总览

接入层结束时，磁盘上多了一批文件和目录，但它们此时还只是「字」：人能读，机器不能比。

这一层要把字变成两样东西：

- **能比的向量**——下次问到相关的问题，它才捞得出来；

- **能用的结论**——一段摘要、一条记忆、一份规则，让下一轮不必再读原文。

这一层把字变成三种产出，各有各的去处：

| 产出 | 落在哪 | 谁做 | 谁用 |
|---|---|---|---|
| L0/L1 摘要 | `.abstract.md` / `.overview.md` | VLM | 检索的第一眼、Rerank 的输入 |
| 记忆条目 | `memories/`（按类型分子目录，另在顶层有三个 md） | VLM（抽取链路） | 下一轮注入上下文 |
| 向量记录 | 向量库 | embedding | 所有检索 |

> 表格里的 L0/L1 摘要与记忆条目都在 OpenViking 的虚拟文件系统之内，是能用 `viking://` 读到的真实文件。

> 向量记录不在虚拟文件系统里，它是另一套独立的存储（称为向量库）。

这一层不做两件事：

- 不决定「谁能看」，那是鉴权与 ACL；

- 不决定「放在哪」，路径在接入层就定了。

它只回答一个问题——**这段内容该被理解成什么**。

## 第一章：用到的模型

名义上 OpenViking 需要两类模型，`ov.conf` 里实际有五个可以填模型的位置。

| 位置 | 是否必需 | 不配时 | 
|---|---|---|
| `embedding.dense` | 必需（有默认） | 回落到本地 `bge-small-zh-v1.5-f16`，512 维 | 
| `vlm` | 必需（无默认） | 摘要、抽取、意图分析全部不可用 | 
| `query_planner` | 可选 | 回退到 `vlm` | 
| `rerank` | 可选 | 关闭，只按向量分数排序 | 未
| `rules.compiler` | 可选 | 回退到账户默认 `vlm` | 

前两个是地基，后三个是可选件。可选件不配也能跑，但各有各的回退路径，这一点后面会反复用到。

## 第二章：embedding——只回答「像不像」

embedding 模型只干一件事：把一段内容压成一个向量，让「相关性」变成可以用距离比较的数字。它不理解含义，也不生成任何文字。

### 三处调用

在 OpenViking 中，有三个地方会调用 embedding 模型，分别是：

1. **入库**：文件正文、目录 L0/L1 各嵌一次，写进向量库。异步，走 embedding 队列。

2. **查询**：每次 `find` / `search` 之前，把查询句嵌成向量（`search` 拆出几条查询就嵌几次，这是「检索有延迟」的直接原因）。

3. **重建**：`reindex`、`processing_mode="vectors_only"` 的重新向量化。

入库的 embedding 有并发限制，而查询则没有（这是为了降低响应延迟）。

### 输入由三个参数决定

| 参数 | 默认 | 作用 |
|---|---|---|
| `text_source` | `content_only` | 嵌正文；`summary_first` 优先嵌摘要，没有摘要再回退正文 |
| `max_input_tokens` | 4096 | 嵌正文时的估算 token 上限，超出截断 |
| `input` | `text` | `text` 或 `multimodal` |

只有 `input: "multimodal"` 才能做「以图搜图」。纯文本模型仍然会索引图片的摘要文本，但查询侧只收文字。

但前提是使用的 embedding 模型本身能支持多模态。

### 元数据不会被 embedding 进向量

L0/L1 进向量时只带一个白名单字段 `directory`；`source`、`generated_by`、`freshness` （元数据）都不进。

换言之，向量只该认「内容」，不该认「这批内容的元数据」。

这样能让「重建索引」和「正常向量化」的输入完全一致，重建后分数不会莫名变化。

### 稀疏与混合

| 对比项 |	密集（dense）|	稀疏（sparse） |
|---|---|---|
| 向量长什么样 |	定长浮点数组，1024 维每维都有小数	| 长度等于词表，绝大多数维是 0 |
| 一个位置代表什么 |	语义空间的一个方向，单维不可解释	| 一个词（或词片），非零值就是它的权重 |
| 怎么判相似	| 比方向：余弦或内积 |	也算内积，本质是「共现了多少关键词」 |
| 擅长 | 同义、改写、跨语言、模糊描述 | 型号、人名、代码标识符、生僻词、精确短语 |
| 短板 | 罕见词与编号不敏感，细节被压平 | 不懂同义，词袋丢语序 |

embedding 模型分为密集和稀疏，混合（hybrid）没有独立的机制，它就是前两路都算一遍，再把两个分数加权合并。

目前来看，OpenViking 支持稀疏和混合检索，但接入的方式很少，只实现了 volcengine、vikingd 两家的 provider 适配。

### 调用 embedding 模型时的三层保护

| 机制 | 默认 | 说明 |
|---|---|---|
| 重试 `max_retries` | 3 | 只对 429、5xx、超时、连接错误；400/401/403 这类永久错误不重试 |
| 退避 | 0.5s 起，上限 8s | 指数退避带随机抖动 |
| 熔断 | 连续失败 5 次断开 | 60s 后放一次探测；探测失败时间翻倍，最长 600s。期间任务重新入队，不丢 |
| 并发 `max_concurrent` | 10 | 只限入库，查询不受限 |

### 不可逆的操作：换模型

官方说「更换模型或 dimension 可能与已有向量集合不兼容，需要迁移或重建索引」，同时表示「修改 embedding 凭证不会迁移历史向量」。

翻译成操作后果：旧向量还在，新向量落在另一个空间里，两批分数不再可比。检索要么报维度错误，要么分数失去意义。

所以换 embedding 模型等于**必须重建索引**，不是「改个配置重启」。

> 换 provider、换 endpoint、换 key 是安全的；换 model、换 dimension 不是。

## 第三章：VLM——把内容压成结论

### 文件摘要 → 目录 L1 → 目录 L0

《OpenViking 深入理解（数据接入层）》讲过自底向上的顺序，这里只补这一层的模型细节：

**文件摘要**由 VLM 依据原始文件内容生成，是纯中间材料，不落盘。

文件摘要是**并发**生成的，并发上限就是 `vlm.max_concurrent`（默认 32），它同时是「语义处理阶段 LLM 并发数」的总闸。

落盘的是目录级的两样东西：

- **目录级** L1（生成预算 `semantic.overview_max_chars`，默认 4000 字符），由 VLM 整合两类内容得到：

  - 本目录下每个文件的文件摘要；

  - 各子目录已落盘的 L0（只读其正文，不读子目录的 L1）。

- 从 L1 正文里提炼出的 L0（预算 `semantic.abstract_max_chars`，默认 256）。

> 父目录 L1 的聚合目前只用于 resource / skill 这两类上下文对应的目录；memory 目录每个目录都不向上冒泡。

拼父目录时，**总输入上限 60000 字符**（`semantic.max_overview_prompt_chars`），超出分批截断。

父目录要不要重写，看 freshness：子目录 L0 正文没变就不往上传播；变了的话：

- 小目录（直接子项不超过 `semantic.overview_sample_limit`，默认 32）立刻刷；

- 大目录累计到 `freshness_refresh_ratio`（默认 0.10）才刷。

注意最后一条的代价：大目录的摘要是「攒够 10% 的变化才重写」，所以在两次刷新之间，它可以是可读但过时的。

> `pending_child_changes > 0` 表示的就是这个状态。

### 多模态理解

在接入层可能会收到多模态的内容，比如用户在会话中发一张图，或者用户上传一段视频作为资源等等。

总的来说，多模态文件也遵守同一条规则：先生成文件摘要，再作为普通文件参与所在目录的 L0 / L1。

因此在语义队列看来，没有单模态与多模态之分，都遵守流程：文件摘要 → 目录 L1 → 目录 L0。

多模态解析发生在图片、扫描页、表格、音视频各有各的 Prompt 模板：

| 对象 | Prompt 模板 | 什么条件下会调 |
|---|---|---|
| 文档内单图（筛选） | `vision.image_filtering` | 文档解析抽出的图，本批只有 1 张 |
| 文档内多图（筛选） | `vision.batch_filtering` | 文档解析抽出的图，本批 ≥2 张，按 5 张一批 |
| 文档内的图（理解） | `vision.image_understanding` | 通过筛选后需要三层信息 | 
| 单个扫描页 | `vision.page_understanding` | 图片化 PDF 的单页 |
| 批量扫描页 | `vision.page_understanding_batch` | 图片化 PDF 的多页 | 
| 表格 | `vision.table_understanding` | 表格**没有**结构化数据（扫描件、图片里的表） | 
| 整份文档 | `vision.unified_analysis` | 有图或无 raw_data 的表 → 视觉通道；都没有 → 纯文本通道 |
| 图像节点摘要 | `parsing.image_summary` | 官方仅记「图像节点摘要阶段」，调用点未公开，**待实测** | 
| 音频 | `parsing.audio_summary` | 音频叶子节点 + `vlm.media.enabled=true` + 格式 ∈ MP3/WAV/AAC/M4A | 
| 视频 | `parsing.video_summary` | 视频叶子节点 + `vlm.media.enabled=true` + 格式 ∈ MP4/AVI/MOV | 

Prompt 模板一个 YAML 文件，把「对模型说的话」参数化。它不是模型，不是配置项——它只决定“怎么问”，不决定“谁来答”。

因为“谁来答”是不确定的，各类 Prompt 模板有执行失败的可能，比如配置的 VLM 不支持多模态，或者是没有配置音频、视频处理工具。

每个 Prompt 模板的**产出**和**失败行为**如下表：

| Prompt 模板 | 产出与失败行为 |
|---|---|
| `vision.image_filtering` | 返回 is_meaningful / reason / image_type；**失败默认保留** |
| `vision.batch_filtering` | 返回 is_meaningful / reason / image_type；**失败默认保留**，返回条数不足的按保留处理 |
| `vision.image_understanding` | abstract / overview / detail_text；**失败降级为 `[Image]` 占位** |
| `vision.page_understanding`  | 三层 + page_num / has_title / title；**失败降级为 `Page N` 占位** |
| `vision.page_understanding_batch` | 必须返回 `pages` 且页数一致；**不一致直接抛错，不降级** |
| `vision.table_understanding` | 三层；有 `raw_data` 时本地生成三层，**不调模型** |
| `vision.unified_analysis` | document / images / tables / sections 一次产出；上限 10 图、20 章节 |
| `parsing.image_summary` | 一段自由文本（`supports_vision: true`），进语义索引 |
| `parsing.audio_summary` | provider 端处理取回文本；**失败或格式不支持 → 空摘要，叶子改用文件名** |
| `parsing.video_summary` | provider 端处理取回文本；`video_fps` 控抽帧；**失败或格式不支持 → 空摘要，叶子改用文件名** |

### 记忆抽取

这是 VLM 最贵的一段，也是唯一会改动已有**记忆条目**的一段。

VLM 会按**记忆类型**逐类提问，每类一份 schema（`memory/*.yaml`（Prompt 模板） 定义字段、文件名模板、目录、合并方式）。

在记忆抽取之前，VLM 会**先预取已有记忆**（`memory.eager_prefetch` 默认开，`prefetch_search_topn` 默认 5）。

于是 Prompt 模板里除了这次对话，还有「你已经知道的事」，`MemoryUpdater` 会据此决定是新建一个 md 还是合并进旧条目。

> 这样的机制保证了同一个实体反复出现不会长出一堆重复文件。

这个环节有三个开关：

- `memory.extraction_enabled`：决定会话提交时是否抽取长期记忆。

- `memory.experimental_memory_switch`：决定 Prompt 模板是否使用实验版，默认关。

- `memory.session_skill_extraction_enabled`：决定是否顺带抽可复用技能，默认关。

### 会话压缩与工作记忆

会话压缩是 VLM 的一个重要的用途。会话提交（commit）后，VLM 先把 `messages.jsonl` 压成可抽取的形态。

用的 Prompt 模板是 `compression.ov_wm_v2`（首次）与 `compression.ov_wm_v2_update`（增量）。

产出的**工作记忆**（working memory）会成为归档概览，也是后面意图分析能看到的上下文。

工作记忆是可选功能，默认不开；不开也不影响长期记忆抽取。

### 检索意图分析

位置是 `query_planner`，不配就回退到 `vlm`。

- 顺序：Account `query_planner` → Account `vlm` → Cluster `query_planner` → Cluster `vlm`。

触发条件很窄：

- 只有 `search`（带 `session_id`）且 `retrieval.enable_intent=true`（默认）才分析；

- `find` 不分析，直接拿查询句去检索。

输入是「压缩摘要 + 最近 5 条消息 + 当前查询」，输出是 0 到数个 `TypedQuery`：

| 字段 | 含义 |
|---|---|
| `query` | 重写后的查询 |
| `context_type` | MEMORY / RESOURCE / SKILL |
| `intent` | 查询目的 |
| `priority` | 1–5 |

输出 0 个是正常结果，不是失败：闲聊、打招呼本来就不该触发检索。反过来，一句「帮我建个 RFC 文档」可能被拆成「技能：创建 RFC 文档」+「资料：RFC 模板」两条查询，分别检索再汇总。

这解释了为什么 DSH 里每步召回**可能**多一次 LLM 调用：插件优先走 `/api/v1/search/search`（带 session），服务端不支持时才退回 `find`。

### 补充：规则编译

`rules.compiler` 是一个独立位，不配就回退到账户默认 VLM。

编译时**强制 `thinking=true`**，并且覆盖模型配置里的默认值。用不支持思考模式的模型，编译会失败——这是本章唯一一条「配了也可能不能用」的能力。

## 第四章：可选模型（临时，只有rerank应保留）

### query_planner

`query_planner`（查询规划）：检索前把一句话拆成 0 到 N 条带类型的查询。

- 输入是压缩摘要 + 最近 5 条消息 + 当前查询，输出 TypedQuery（query / context_type / intent / priority 1–5）。
  
- 存在的主要理由是分流：这一步每轮对话都可能跑，难度低但对延迟敏感，值得单独用一个便宜快模型。

### rules.compiler

`rules.compiler`（规则编译）：把一条指令或资料编译成规则 Markdown，

- 规则 Markdown 带 `applies_when` 和 `exception` 条件，存在 `memories/rules/<scenario>/` 下，日后按当前任务检索「这次适用哪几条」。

- 它的特点是强制 `thinking=true`，并且会覆盖模型配置里的默认值。

### rerank

`rerank`（精排）：对向量召回的候选再排一次序。

- 它并不属于「换一个更大的 LLM」那一类；它属于 `cross-encoder`，输入是一对文本 (查询, 候选)，输出 0–1 的相关性分数。

## 第五章：可调旋钮

### 想更准

| 旋钮 | 说明 |
|---|---|
| 配 `rerank` | `threshold` 默认 0.1；THINKING 模式取 2 × limit 候选 |
| 配 `sparse` / `hybrid` | 需要 `volcengine` 或 `vikingdb`，并开 `sparse_weight` |
| 用 `input: multimodal` 的 embedding | 唯一能做以图搜图的方式 |
| 改 `prompts.templates_dir` 下的摘要、意图模板 | 见下节风险分级 |

### 想换语言与口径

- `output_language_override`：摘要、目录概览、工作记忆、记忆抽取都跟它走；留空是自动识别，显式 `""` 是强制自动识别。图片摘要不吃这个开关，音视频优先用媒体自身语言。

- `prompts.templates_dir`（或环境变量 `OPENVIKING_PROMPT_TEMPLATES_DIR`）：覆盖普通模板，同名同路径优先，未命中回退内置。

- `memory.custom_templates_dir`：新增记忆类型或改写已有类型。后加载的同名 `memory_type` 覆盖先前的。

### 改 prompt 的风险分级

官方给的分级，值得记住：

| 改什么 | 风险 |
|---|---|
| 措辞、加例子、调语气 | 低 |
| 摘要粒度、抽取偏好、输出风格 | 中 |
| 变量名、输出结构、记忆字段名 | 高 |
| `directory`、`filename_template`、`merge_op` | 很高 |

最后一行之所以「很高」：它改的不是模型说什么，而是东西**写到哪、叫什么、怎么合并**。改完，历史文件还在老位置，新文件去了新位置，检索范围跟着变。

> 保守做法：先复制模板，只改指令内容和表达方式，结构字段最后再动；每次只改一类，方便定位影响。
