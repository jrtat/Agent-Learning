# OpenViking 深入理解（语义处理层）

## 序言

> date: 2026/11/11

由大肥鱼创作，我负责校对。目的是更细致地介绍 OpenViking 的理念、架构、功能和执行流程。

目前计划从五个层次理解 OpenViking 的内部架构，这是第三节：语义处理层。

这一篇只回答一个问题：**数据落盘之后，OpenViking 对它做了什么**。具体来说，要讲清三件事：

- 哪些内容会被加工、加工成什么、加工完存在哪；

- 上下文类型不同，走的路径差在哪；

- 模态不同，处理差在哪。

重排序与检索意图分析不在这里。它们发生在「读」的时候，属于下一篇。

## 总览

接入层结束时，磁盘上多了一批文件和目录，但它们此时还只是「字」：人能读，机器不能比。

这一层把「字」变成两样东西：

- **能比的向量**——下次问到相关的问题，它才捞得出来；

- **能用的结论**——一段摘要、一条记忆、一份规则，让下一轮不必再读原文。

拆开是三种产出：

| 产出 | 形态 | 落在哪 | 谁生成 |
|---|---|---|---|
| 目录摘要与概览 | 每个目录一份 `.abstract.md`、一份 `.overview.md` | 目录内，隐藏文件 | VLM，走语义队列 |
| 记忆条目 | 一条一个 `.md` | `memories/` 下按类型分目录 | VLM，走抽取链路 |
| 向量记录 | 一条可独立命中的片段 | 向量库 | embedding 模型 |

三者有先后：摘要先有，向量才有东西可嵌；记忆先抽出来落盘，再作为普通文件被向量化。

这一层不决定：

- 「谁能看」，那是鉴权与 ACL；

- 「放在哪」，路径在接入层就定了。

它只回答一个问题——**这段内容该被理解成什么**。

## 第一章：分岔——类型决定路径，模态决定入口

### 参与语义处理层的数据

同样是「落盘之后」，各类数据并不走同一套处理。

| 数据 | 入口 | 语义队列 | 目录级摘要 | 进向量库 | 向父目录冒泡 |
|---|---|---|---|---|---|
| 资源 | 解析 → 写盘 | 走 | 有 | 进 | 是 |
| 技能 | 直接写盘 | 走 | 有，形态不同 | 进 | 是 |
| 记忆 | 抽取 → 写盘 | 走 | 条目没有，目录几乎不产生 | 进 | 否 |
| 规则 | 编译 → 写盘 | 不走 | 只有 L0 | 进，按记忆处理 | 否 |
| 会话 | 提交归档 | 不走 | 默认没有 | 不进（归档只作抽取输入） | 否 |
| 工具 | 登记 / 挂载 → 写盘 | 走 | 随所在目录；根为建库话术 | 进：定义走工具检索，节点走通用 | 否 |

四点解释：

- 「走语义队列」指的是由语义队列生成 L0 / L1。不走的，要么另有写手（规则编译器），要么根本不需要。

- 「冒泡」指子目录摘要变化是否触发父目录重写。只有资源与技能这么做；其余几类的摘要各自独立，不往上聚。

- 记忆那一行还有两处例外：

  - 它确实会经过同一个语义入口，但目录级的 L0 / L1 基本不产生（条目本身就是提炼过的短文本）；

  - 记忆条目的向量直接取正文，不再另做摘要。

这张表只标差异。每一步具体做什么，后面几章展开。

### 模态只在两头出现

模态影响的是「怎么变成文本」和「什么时候变」。一旦变成本文，后面就同构了。

所以它只落在两处：

- **进门时**：资源里的图、扫描页、表格、音视频，由解析器在解析阶段转成正文；代码文件走另一条路线（提取代码骨架），不整篇给模型。

- **抽取时**：会话里发的图片不在解析期处理，要等提交之后、记忆抽取那一步，才由 VLM 描述成一段文本。

变成本文之后，就是同一条流水线：文件摘要 → 目录 L1 → 目录 L0 → 向量化。

## 第二章：摘要——从文件到目录

### 文件摘要只是材料

摘要链路的第一步，是给目录下的每个文件生成一句摘要。

它有三个特点：

- **并发**：上限是 `vlm.max_concurrent`（默认 32），这一个数字同时是整段语义处理的 LLM 并发总闸。

- **不落盘**：文件摘要只用来拼材料，不存成文件，也不单独进向量库。

- **看内容**：它依据正文生成；对代码文件，依据的是代码骨架（导入、类、方法、函数等符号），取不到骨架才回退成普通文本摘要。

> 所以「文件也有摘要」只在过程中成立。磁盘上能读到的摘要，都是目录级的。

### L1 由什么拼成

目录概览 `.overview.md`（L1，默认 4000 字符）由两类材料拼成：

- 本目录下每个直接子文件的文件摘要；

- 每个直接子目录已经落盘的 L0 正文。

两个容易记反的地方：

- 只读子目录的 **L0**，不读子目录的 L1。L1 是一层一层搭上去的，不是把整棵子树倒进去。

- 只读正文，不读 frontmatter。`source`、`generated_by`、`freshness` 都不进 prompt，避免元数据污染摘要。

直接子项超过采样上限（默认 32）时，改用稳定采样：同一棵树重复刷新会选到同一批样本，减少摘要的随机漂移。

拼父目录时还有总输入上限（默认 60000 字符），超出就分批截断。

### L0 怎么来

L0（`.abstract.md`，默认 256 字符）是目录的一句话。

对资源目录，它不是「再让模型压一次」，而是**从 L1 正文里取一段**：H1 标题之后、第一个二级标题之前的简述段。

- 预算按字符算，截断时尽量保留完整句子。

另有一条捷径：建目录时可以直接给一句说明，没给就用目录名。

所以**只有 L0、没有 L1 的目录是合法状态**，读取与重建都只处理实际存在的层级。

### 三种 L0，三种写法

同样是 L0，来源不同，形态也不同。

| 类型 | L0 从哪来 | 形态 |
|---|---|---|
| 资源目录 | L1 正文里的简述段 | 散文 |
| 技能包根 | `SKILL.md` 的头部元数据序列化 | 一段 YAML：名称、描述、标签、可用工具 |
| 规则目录 | 规则编译器写入 | 规则集的提要 |

技能还有两条特别之处：包根的 L1 是技能正文整段，不是「包内文件摘要的聚合」；往包里加附件不会动包根这两条记录。

### 自底向上与 freshness

语义队列只从下往上跑：叶子目录 → 父目录 → 一直到命名空间边界。父目录的材料来自子目录，子目录没摘要，父目录就没材料。

父目录要不要重写，看 freshness。它记的是直接子项的覆盖情况。

| 字段 | 含义 |
|---|---|
| `total_entries` | 参与语义的直接子项总数 |
| `sampled_entries` / `unsampled_entries` | 本轮用了多少、漏了多少 |
| `pending_child_changes` | 已知落后于下层、但还没反映到正文里的变化数 |

判断规则：

- 子目录 L0 正文没变，不向上传播；

- 变了，小目录立即安排刷新；

- 大目录累计 `pending_child_changes`，与总数之比达到阈值（默认 0.10）才刷新。

代价是：**大目录的摘要是「攒够一成变化才重写」的**。两次刷新之间，它读得通，但已落后。`pending_child_changes > 0` 表示的就是该状态。

阈值策略不承诺定时刷新。要立刻更新，只能手动触发。

### 哪些目录比较特殊

**规则上下文所对目录**：摘要由编译器写，只有 L0，没有概览。

**会话所对目录**：提交后默认不产生归档摘要；开了工作记忆，才有一份由压缩产出的概览。

**记忆上下文所对目录**：条目本身就是提炼过的短文本，不再生成条目级摘要；目录级也几乎不产生。

**固定目录**：`memories/`、`agent/tools/` 这类根的 L0/L1 是建库时写死的固定话术，不是模型生成的。

**`system/`**：完全不处理。

## 第三章：模态——两条入口，一个终点

### 通过资源接入：解析期就变成文本

资源导入时，多模态内容在**解析阶段**被转成文本，靠的是一组视觉与媒体模板。按对象分：

| 对象 | 什么时候调 |
|---|---|
| 文档里的图（筛选） | 先判断这张图有没有信息量 |
| 文档里的图（理解） | 通过筛选后，产出摘要、概览、细节三层 |
| 图片化 PDF 的页 | 单页一套、多页一套 |
| 表格 | 仅当表格没有结构化数据（扫描件、图片里的表）；有数据则本地生成，不调模型 |
| 整份文档 | 有图，或表格没有可用数据 → 走视觉通道；否则走纯文本通道 |
| 音频 / 视频 | 需要显式开启媒体理解，且格式在支持范围内 |

这些模板的产出会变成资源节点里的**正文**，也就是 L2。之后它和一份普通文本没有区别。

### 通过会话接入：抽取期才变成文本

会话里发的图片不在解析期处理。它要等到会话提交、进入记忆抽取那一步，才由 VLM 描述成文本，作为抽取的输入。

两处的区别值得单独记。

| | 资源路径 | 会话路径 |
|---|---|---|
| 时机 | 解析期 | 提交之后的抽取期 |
| 产出 | 正文（L2），会落盘 | 一段临时描述，不成为 L2 |
| 之后 | 摘要 → L0/L1 → 向量 | 只喂给抽取链路 |

### 失败怎么降级

多模态是这一层最容易失败的地方，降级因此分档。

| 环节 | 失败时 |
|---|---|
| 图片筛选 | 默认**保留**——宁可多留，不可错杀 |
| 单图理解 | 降级成占位符：位置还在，内容没了 |
| 扫描页理解 | 降级成「第 N 页」占位 |
| 批量扫页 | 页数对不上直接报错，不降级 |
| 音视频理解 | 空摘要，节点改用文件名 |

共同点：**原文不受影响**。摘要可以缺、可以是占位，文件本身已经在磁盘上了。

## 第四章：向量化——只回答「像不像」

### 它只做一件事

embedding 模型把一段内容压成一个向量，让「相关性」变成可以比距离的数字。它不理解含义，也不生成文字。

它出现在三个地方。

| 时机 | 嵌什么 | 特点 |
|---|---|---|
| 入库 | 文件正文、目录 L0/L1 | 异步，走向量化队列，有并发上限 |
| 查询 | 查询句（拆成几条就嵌几次） | 同步，不受入库并发限制 |
| 重建 | 重新向量化 | 与入库用同一套输入规则 |

入库限流、查询不限流，是为了不让响应延迟被后台任务拖住。

### 输入由三个参数决定

| 参数 | 作用 |
|---|---|
| `text_source` | 嵌正文，还是优先嵌摘要（没有摘要再回退正文） |
| `max_input_tokens` | 嵌正文时的估算上限，超出截断 |
| `input` | 纯文本，还是多模态（多模态才能「以图搜图」） |

「优先嵌摘要」是个有代价的优化：省 token，但检索匹配的是**摘要的语义**。正文里有、摘要里没提的细节，不是分数低，而是根本进不了候选。

> 只有 embedding 模型本身支持多模态，多模态开关才有意义。

### 元数据不进向量

L0/L1 进向量时只带一个白名单字段：`directory`。`source`、`generated_by`、`freshness` 都不进。

目的很实际：让「正常向量化」和「重建索引」的输入完全一致。否则重建一次，同一段内容的分数会莫名变化。

### 密集、稀疏与混合

| | 密集（dense） | 稀疏（sparse） |
|---|---|---|
| 向量形态 | 定长浮点数组，每维都有值 | 长度等于词表，绝大多数是 0 |
| 一个位置 | 语义空间的一个方向，单维不可解释 | 一个词或词片，非零值就是权重 |
| 擅长 | 同义、改写、跨语言、模糊描述 | 型号、人名、代码标识符、生僻词 |
| 短板 | 罕见词与编号不敏感 | 不懂同义，丢语序 |

混合检索就是把两路分数加权合并。当前支持稀疏与混合的后端适配不多，主要落在两家云服务上。

### 失败与不可逆

调用侧有三道保护。

- **重试**：只对限流、服务端错误、超时、连接错误重试；参数错、鉴权错这类永久错误不重试。

- **退避**：指数退避带随机抖动，逐步拉长间隔。

- **熔断**：连续失败到阈值就断开一段时间；期间任务重新入队，而不是丢掉。

另有一条不可逆的：**换模型等于换空间**。

旧向量还在，新向量落在另一个坐标系里，两批分数不再可比。检索要么报维度错，要么分数失去意义。所以换 embedding 模型必须重建索引，不是改个配置重启。

> 换服务商、换地址、换密钥是安全的；换模型、换维度不是。

### 边界：有向量不等于搜得到

- `system/` 整支不向量化，只读，所以永远搜不到。

- 工具节点会按 `resource` 类型被处理、也会产生向量，但它不在默认召回范围里，实际只能按路径读，或走工具检索。

- 规则不出现在记忆类型表里，但按路径会被判成记忆，字段处理与记忆一致——所以它进得了检索，只是身份算记忆。

## 第五章：会话——压缩与工作记忆

### 提交之后分成几件事

会话提交把一批未归档消息交出去。之后它们走向几个不同的产物。

| 产物 | 干什么用 | 默认 |
|---|---|---|
| 压缩结果 | 把消息流整理成可抽取的形态 | 只作中间材料，不落盘 |
| 长期记忆 | 把事实、偏好、实体、事件沉淀成条目 | 开 |
| 工作记忆（压缩结果的落盘形态） | 给这一段对话一份可读的归档概览 | 关 |

三者来自同一次提交，但开关互不牵连：工作记忆关着，只影响概览落不落盘，不影响长期记忆抽取。

### 压缩：先整篇，后打补丁

压缩是抽取链路的第一步。

开了工作记忆，压缩结果会落成一份可读的概览。它的写法不是每次重压一遍：

- **首次**整篇生成；

- **之后**按节写补丁——哪几节保留、哪几节更新、哪几节追加。

所以成本随对话增长是线性的，不是平方的。

### 工作记忆是什么，不是什么

它是压缩的产物，会成为归档的概览，也是后续「读懂这一轮在问什么」的输入之一。

它不是长期记忆：它描述「这段对话怎么走到这里」，不描述「关于你和世界的事实」。两者落点不同，生命周期也不同。

它是可选功能，默认关闭。关闭时归档里没有概览文件——这不是漏了，是没开。

## 第六章：记忆——抽出来的结论

### 为什么会话要一条单独的链路

其他几类数据是「一份内容，一次加工」。会话不是：一批消息里可能同时有事实、偏好、实体、事件、任务过程，必须**按类型分头问一遍**。

所以会话的链路比别的长一步：先压缩，再抽取。

### 三步

1. **压缩**：把原始消息整理成可抽取的形态。

2. **逐类抽取**：按记忆类型一类一类地问「这段对话里有没有这类信息」。

3. **更新**：决定新建一条，还是合并进已有条目。

第二步的 schema 不是提示词，而是**写盘规则**：字段有哪些、文件名怎么拼、落在哪个目录、多条之间怎么合并。

这也解释了为什么「加一种记忆类型」是加一份模板，不是改代码。

### 先看已知，再决定写什么

抽取之前，系统会按当前对话预取一批已有记忆。

于是模型看到的不只是这次对话，还有「你已经知道的事」，更新器据此决定新建还是合并。

> 这样同一个实体反复出现，不会长出一堆重复文件。

### 类型不同，生命周期也不同

| 类型组 | 写法 | 生命周期 |
|---|---|---|
| 文件型（画像、助手自我设定等） | 一类一份文件 | 反复覆盖 |
| 目录型（偏好、实体、事件等） | 一条一个文件，按主题或日期分子目录 | 偏好、实体会被覆盖；事件只增不改 |
| 执行派生（案例、轨迹、经验） | 目录型 | 由任务过程决定，不一定产出 |

执行派生那一组还有一道门槛：**先有案例，才有轨迹与经验**。

原因是后两者都是「任务执行」的产物：轨迹讲「这类任务怎么一步步做」，经验讲「做完之后总结出什么」。没有可复用的案例，就没有可提炼的对象。

### 开关与边界

- **抽取总开关**：决定提交时是否抽长期记忆。

- **实验模板开关**：是否用实验版 schema 覆盖同名内置类型。

- **技能抽取开关**：是否顺带抽可复用的会话技能，默认关。

- **类型清单**：哪些类型会被抽是一份显式清单；有模板但不在清单里的，不会被抽。

- **可编辑范围**：只有部分类型的内容模板允许按账号覆盖，其余直接拒绝。

还有一个容易被忽略的入口：导入资源时如果带上「导入原因」，这段原因会送进抽取链路，写进常规记忆类型。这是资源侧唯一能顺手写记忆的口子。

## 第七章：规则——编译出来的约束

### 不是抽的，是编译的

规则和记忆长得像（都放在 `memories/` 下），来历完全不同。

| | 记忆 | 规则 |
|---|---|---|
| 触发 | 会话提交 | 显式发起编译 |
| 输入 | 对话 | 一段指令，或最多十几份资料 |
| 产物 | 一条条事实 | 一组带适用条件的约束 |
| 变更 | 反复覆盖 | 显式启停、替换、归档 |

普通会话提交**不会**触发规则编译。这是两者最大的区别。

### 输入与动作

编译的输入有两种：一段约束文本，或一批来源（已有资源、远程地址、本地上传）。来源会先走一遍资源导入，再从中抽约束。

产出的动作是显式的，不是自由发挥：新增、更新、替换、无操作，外加暂停、恢复、归档这类生命周期动作。说不清楚的会记成「不确定」或「拒绝」，不落盘。

编译时强制开启思考模式——先写推理，再给结论，并覆盖模型配置里的默认值。用不支持思考模式的模型，编译会失败。

### 产物形状

规则落在规则目录下，按场景分组：每个场景一份 `abstract.md`（L0），加若干条规则文件。

注意它**没有概览**（L1）。这也是它不进语义队列的直接证据：那条链路的标准产出是成对的 L0/L1。

规则有三种状态：生效、暂停、归档。暂停的仍可被重新编译覆盖，但不再参与召回；归档是逻辑删除，保留一段时间。

### 身份的错位

规则借用记忆的位置，身份却是规则：按路径会被判成记忆，所以字段处理、向量化都跟记忆一致，但它不出现在记忆类型表里。

## 第八章：支撑——模型、模板与队列

### 模型：五个位置，两条必需

名义上要两类模型，配置里实际有五个位置。

| 位置 | 必需 | 不配时 |
|---|---|---|
| 向量模型 | 是（有默认） | 回落到本地小模型 |
| 视觉语言模型 | 是（无默认） | 摘要、抽取、编译全部不可用 |
| 查询规划 | 否 | 回退到视觉语言模型 |
| 重排序 | 否 | 关闭，只按向量分排序 |
| 规则编译 | 否 | 回退到账号默认模型 |

后三个是可选件，各有回退路径。所以「没配某项」通常不是报错，而是降级。

### 模板：决定「怎么问」，不决定「谁答」

模板是参数化的问题。它不是模型，也不是开关：改模板不换模型，只换问法。

这里有两套东西，配错地方不会报错，只会静默不生效。

| 模板 | 决定什么 |
|---|---|
| 提示词模板 | 模型「怎么说」：视觉、解析、摘要、压缩…… |
| 记忆模板 | 记忆「长什么样、写哪里」 |

判断风险只有一条：**改的是「模型说什么」，还是「系统怎么解析、往哪儿写」**。

- 改措辞、加例子：低风险。

- 改摘要粒度、抽取偏好：中风险，结果分布会变。

- 改输出结构、字段名：高风险，调用方按旧结构解析会读不到。

- 改目录、文件名模板、合并方式：很高风险，改的是写盘行为。

> 稳妥的做法是只改指令内容，结构字段最后再动；一次只改一类。

改完要重启：提示词有缓存，记忆模板还要重建注册表。

### 队列：分池排队，坏了能补

这一层的重活都是异步的，而且分池排，不是一条大流水线。

| 队列 | 干什么 |
|---|---|
| 资源入库 | 解析、建树、写盘 |
| 外部解析 | 调用外部解析服务 |
| 正文落盘 | 写内容存储 |
| 语义 | 目录 L0/L1 |
| 节点语义 | 节点级语义 |
| 向量化 | 算向量 |
| 会话提交 | 归档 |
| 重建索引 | 重新向量化 |
| 用户删除 | 清理 |
| 外部任务 | 其他 |

分池的意义：一条堵了不连坐。入库慢不会挡住会话提交，解析服务挂了也不会让已落盘的内容写不进去。

因为异步，就会有「处理到一半」的状态。为此留了三个补做口子。

- **目录缺摘要**：可以显式要求给某个目录补 L0/L1，不必等下次排队。

- **归档失败**：可以对指定归档显式重试，并带内容哈希防覆盖。

- **索引不一致**：重建索引。

> 不积压时这些计数全是 0，看不出分工；一旦有堆积，先看是哪条队列，再往回找卡在哪一步——比笼统说「处理慢」有用得多。

### 语言：一个开关管五处，两处例外

输出语言是账号级、可运行时修改的开关，管五处：文本资源摘要、目录概览、工作记忆、记忆抽取、手动记忆整理。

它有三态，不是两态：不写（跟随上级）、显式空（强制自动识别并覆盖上级）、具体语言（固定）。

两个例外：图片摘要不吃这个开关；音视频优先用媒体自身的语言。

### 检索意图分析

检索之前，把「当前这句 + 前面几轮」交给 `query_planner`（不配就回退到 VLM），让它产出零到数条带上下文类型的查询，再分别去检索。

> 它是**召回链路**上的第一道加工，不是检索本身。

只有在以下三个条件同时满足时，才会执行检索意图分析：

- 检索走的是 `search`，不是 `find`；

- 请求带 `session_id`；

- `retrieval.enable_intent=true`（默认）。

> 检索走 `find` 时不进行检索意图分析，直接拿原句去检索；`grep`、`glob`、`ls` 这些根本不经过这里。

检索意图分析的**输入**有三样：

- 当前会话的压缩摘要：会话的工作记忆/归档摘要；

- 最近 5 条消息：服务端会话记录里的最近几条（一般含 Assistant 回复，即大语言模型的回答）；

- 当前这句查询：这一轮用户打的字（连发几条会合并）。

检索意图分析的**输出**是一组 `TypedQuery`：

| 字段 | 含义 |
|---|---|
| `query` | 重写后的查询 |
| `context_type` | MEMORY / RESOURCE / SKILL |
| `intent` | 查询目的 |
| `priority` | 1–5 |

这些查询是怎样被用到的：**多条是各查各的，再合并。**

- 常被忽略的后果：`search` 的 `limit` 是**每条规划查询**的上限，不是总数；合并后总数可能超过它，且当前不保证跨查询去重。

- 输出为 0 条是正常结果，此时这一轮不检索。打招呼、闲聊本来就不该触发召回；把它当「检索失败」去排查是白费劲。

插件优先走 `/api/v1/search/search`（带 session），服务端不支持时才退回 `find`——退回之后这一步就直接不存在了。

### 重排序

#### 为什么需要重排序

向量检索是「双塔」：查询和文档各自独立编码成向量，最后只比一次距离。

它的优点是能事先为全库建好索引，要处理几百万条也只要一次近邻查询；

缺点在于两边从未一起看过，模型无法判断「这一段是否正好回答了这句话」，只能判断「两边语义是否接近」。

于是常见情形是：相关内容全都召回了，只是排在前面的不是最该看的。

#### 为什么重排序更准

rerank 是 cross-encoder：把（查询，候选）作为输入送进同一个模型，让两段文字在模型内部逐 token 交互，输出一个 0–1 的相关性分数。

因为它每次只看一对，无法预先建索引，所以只能用在小候选集上——这就是它「更准但更贵」的原因。

换句话说，向量召回负责海选，rerank 负责复评。

> 在 OpenViking 中，候选文本取的是向量记录里的 abstract 字段（展示用的那段摘要），不是 L2 正文。

> 所以摘要写得含糊，精排也会跟着含糊——这是「摘要质量会影响排序」的一条隐蔽链路。

#### 在 OpenViking 里的位置

- 不配 rerank 就默认关闭，只按向量分数排序；rerank 没有独立的 enabled 字段，凭据齐全才算启用。

- list 模式下候选数是 2 × limit：先宽取，再精排取前 limit，不会因为精排而多召回。

- 默认阈值 `rerank.threshold: 0.1` 只过滤 rerank 分；请求里的 score_threshold 优先级更高。

- 纯向量路径（`find`）从不 rerank；图片查询跳过。

- `search` 的 context 模式默认也不 rerank，要显式打开 `retrieval.apply_rerank_to_context` 才按配额桶各排一次。

- rerank 只处理本次召回的候选，不会因为分数低就发起第二轮检索。
