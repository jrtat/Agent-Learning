# OpenViking 深入理解（上下文存储层）

## 序言

> date: 2026/11/11

由大肥鱼创作，我负责校对。

目的是更细致地介绍 OpenViking 的理念、架构、功能和执行流程。

目前计划从五个层次理解 OpenViking 的内部架构，这是第一节：上下文存储层。

在这个章节中，我们将一窥 OpenViking 的虚拟文件系统的全貌。

## 总览

在这一层，我们以 Studio 中能看见的虚拟文件系统为切入点，理解 OpenViking 的上下文存储。

官方「上下文类型」把上下文分成四类：**Resource**、**Memory**、**Skill**、**Rule（Beta）**。

但“上下文存储层”在实现上是另一套东西：`viking://` 的作用域、作用域里固定的子目录，以及目录可能携带的摘要文件。

类型决定生命周期和由谁写入，存储结构决定权限和读取成本，两者不能互相替代。

## 第一章：四个作用域

`viking://` 下有四支：`user` / `agent` / `resources` / `system`。前三支的关系是“谁能看见”，最后一支回答的是“什么是内置的”。

### user 子目录

`viking://user/<id>/`：默认只有用户自己能看。哪怕用 ADMIN 身份也不能读别人的 user 路径。

- ROOT 可以跨用户读；但在 api_key 模式下 ROOT key 调不了数据 API，这条能力只在 trusted 等模式下可用。

- `viking://user/` 下都是按用户 ID 命名的目录，正如后续章节展示的那样，这些文件夹的内部结构是类似的。

### agent 子目录

`viking://agent/`：在账号内共享的能力与配置目录，其子目录分别如下所示：

- `skills/`：共享技能

- `tools/`：共享 MCP 工具的挂载点，读这里的节点等于实时调用外部工具。

- `endpoints/`：规划中，本实例为空

- `payments/`：规划中，本实例为空

> `viking://agent/` 没有 `memories`：官方明确说明记忆不使用独立的 `viking://agent/memories`，记忆只放在 user 或 peer 命名空间。

### resources 子目录

`viking://resources/`：账号共享的资料区，可以用 ACL 按目录授权。

### system 子目录

`viking://system/`：0.5.4 新增的只读作用域，装 OpenViking 自带的两类资产，不属于任何账号或用户：

- `compile/example-skills/`：四个示例技能（`daily-report`、`knowledge-distillation`、`llm-wiki`、`ov-session-report`），供 `ov compile` 与 Studio 的「编排」「编译」使用；

- `memory/memory_templates/`：`builtin/` 是 11 份内置记忆模板（`cases`、`entities`、`events`、`experiences`、`identity`、`preferences`、`profile`、`skills`、`soul`、`tools`、`trajectories` 各一份 `.yaml`，另有一个 `experimental_memory/` 目录），`custom/` 是唯一可写的位置。

它在命名空间策略里被单独划出来，判据是 `NamespaceProcessingMode.FILE_ONLY`：

- 不支持 ACL、不支持标签、不支持重建索引；

- 不进语义队列，不生成 `.abstract.md` / `.overview.md`，也不向量化。

换句话说，`system/` 里的文件能读、能当模板用，但永远不会变成检索结果。

固定目录本身不可写，只有 `memory_templates/custom/` 下的资产可以写，写进去按 Account 生效，一个记忆类型一个文件（`<memory_type>.yaml`）。

## 第二章：六个固定子目录

`viking://user/<id>/` 中的六个子目录是平台固定下来的，不要自行改名；能扩展的是记忆类型，不是这六个目录。

> 0.5.4 之后这里仍然是这六个，没有多出 `settings/`。容易看错的“设置”是服务端的一份配置接口，不落在虚拟文件系统里，见文末「补充：设置层与策略」。

| 子目录	| 谁写入	| 装什么	| 
|---|---|---|
| `memories/` | 会话提交后的抽取任务 | 长期记忆；规则编译后另有 `rules/` |
| `sessions/` | 每次对话由插件写入 |	消息流、工具结果、归档、召回日志	|
| `resources/` |	你导入资料时	| 个人私有文档 |
| `skills/` |	安装技能时	| `SKILL.md` 与配套脚本 |	
| `peers/` |	写入带 `peer_id` 的记忆或 peer 资料时 | 关于某个交互对象的记忆与资料 |	
| `privacy/` | 安装技能或登记密钥时 | 敏感配置的分版本快照 |

最容易看漏的是 `sessions/` 也在 user 作用域里：会话不是“另一个系统”，它本身就是一棵目录树，和记忆同源同层。

`privacy/` 的目录按 `privacy/<category>/<target_key>/` 组织，`category` 目前只有 `skill`、`session`、`credential` 三类：

- `skill` 在写入技能时自动抽取；

- `session` 的正文替换在用、但新值自动探测被官方暂时禁用；

- `credential` 由人手动登记（如 `github` 的 PAT）。

`peers/` 按 `peer_id` 命名，每个目录下只有 `memories/` 与 `resources/` 两个位置，详见后面的「补充：peer 内部」。

## 第三章：memories 内部按类型分家

`viking://user/<id>/memories/` 下登记了 8 个目录型、3 个文件型记忆类型。

这 11 种是「类型」而不是「现成的目录」：类型按需创建。

与六个固定子目录不同，记忆类型可由记忆模板扩展或调整。

| 记忆类型	| 子目录 |	装什么 |	
|---|---|---|
| preferences	| `memories/preferences/` |	按主题组织的偏好 | 
| entities |	`memories/entities/` |	人、项目、工具等实体知识 |
| events |	`memories/events/年/月/日`	| 决策、里程碑、发生过什么 |
| cases	| `memories/cases/`	| 训练与评测用的任务案例 |
| trajectories |	`memories/trajectories/`	| 可复用的执行轨迹 |
| experiences	| `memories/experiences/`	| 从执行结果提炼的经验 |
| tools | `memories/tools/` | 官方默认关闭，仍登记在类型表中 |
| skills | `memories/skills/` | 官方默认关闭，仍登记在类型表中 |
| profile |	`memories/profile.md`	| 你是谁：身份、职业、关系等 |
| identity | `memories/identity.md`	| 助手自己的名字、形象、自我介绍 |
| soul | `memories/soul.md`	| 助手的核心原则与边界 |

表格只列了位置，有四点需要单独说：

**其一**，`identity.md` 与 `soul.md` 并不是关于“用户”的画像，而是助手自己的自我设定。

- `identity.md` 里是待填的 Name / Creature / Vibe 字段；

- `soul.md` 里是 “Be helpful, not performative” 这类原则。

这跟“记住用户”是两件事。

**其二**，`entities` 和 `events` 都再分了子目录，这也是它们看起来最“乱”的原因：

- **`entities`** 按主题（比如：人物、学术论文、工具、开源项目、教材_讲义、文档、概念、系统等，都是根据实际对话归纳的）。
  
- **`events`** 按事件发生日期分年/月/日，如 `memories/events/2026/11/09/`。

**其三**，`cases`、`trajectories`、`experiences` 是成组出现的，也是上表里唯一一组带有「训练」环节的记忆。

它们归在「Agent 演进」这条流水线下，彼此有前后依赖，不是三个并列的目录：

- 会话提交时，抽取器先在对话里找 `cases`——一段可训练、可评估的任务过程，含目标、步骤与结果；
  
- 只有产出 `case` 后，才会继续训练 `trajectories`（从任务轨迹提炼的可复用操作契约）与 `experiences`（从执行结果提炼的可复用经验）；

- 反过来不成立：没有 case，另外两个目录不会自己长东西。

这条流水线默认是关的。开关是 `server.agent_evolution.enabled`，写在 `ov.conf` 里，默认 `false`。

它是部署级的，改完要重启服务，且只影响之后的提交。

**其四**，`memories/rules/` 里放的是规则（Rule，Beta），它不在上表里——表列的是记忆类型。

规则只是「借位」存放：位置在 `memories/` 下，读写却走独立的编译与搜索接口。规则不是写进去的，是编译出来的：

- `POST /api/v1/rules/compile` 从一条指令或一批资料里提炼强约束，落成 `memories/rules/<scenario>/` 下的两样东西：

  - `abstract.md`（这个 Scenario 是什么情况）；

  - 具体规则文件（约束正文、适用条件 `applies_when`、例外、原文证据）。

- 它跟记忆的生命周期刚好相反：

  - 记忆是抽出来的、会不断被 upsert；

  - 规则是编译一次、由人启停。

- 普通会话提交不会触发规则编译，也没有「每轮强制注入规则」的机制，召回全靠 `rule_search`。

- 规则有三种状态 `active`、`paused`、`archived`——暂停的仍可被重新编译覆盖，但不再参与召回；归档是逻辑删除，保留期默认 30 天。

- 召回默认只返回适用分数达到 0.65 的规则。

## 补充：peer 内部

每个 `viking://user/<id>/peers/<peer_id>/` 下只有两个位置：

| 位置	| 装什么	| 什么时候出现 |
|---|---|---|
| `viking://user/<id>/peers/<peer_id>/memories/` | 关于这个对象的记忆，子结构与用户根同源 | 首次抽取写入时 |
| `viking://user/<id>/peers/<peer_id>/resources/` | 与这个对象相关的资料 | 只有人往里放资料时 |

所以 peer 下没有 `sessions/`、`skills/`、`privacy/`——这三个只属于 user 空间。

`memories/` 的结构跟用户根基本一致——同一套记忆模板，只把 `{{ user_space }}` 从 `<id>` 换成 `<id>/peers/<peer_id>`。

区别只在能落进来的类型：

- `profile.md` 记的是这个对象的长期状态，不是用户画像；一个 `profile.md` 里可以有多名参与者，每人一个 H1；

- `preferences/`、`entities/`、`events/` 的语义同样以该 peer 为主体；

- `cases/`、`trajectories/`、`experiences/` 只有 user 根会有，peer 下永远不会存在。

- `identity` 与 `soul` 描述助手自身，几乎不会挂到某个 peer 下。

两点边界，外加一条时机提醒：

- peer 不是身份，不能单独签发凭证，也不能单独作为 ACL 授权对象；

- `sessions/` 属于用户空间，不挂在 peer 下；

- peer 目录不是预建的，对着空 `peers/` 判断“peer 没生效”并不可靠，要看 `memories/` 下有没有文件。

## 补充：session 内部

每个 `sessions/<session_id>/` 的结构是：

- `messages.jsonl`（消息流）

- `history/`（归档）
  
- `tool-results/`（有工具调用时才出现）

- `.recall_log.json`（这次会话召回了哪些上下文）

会话提交后 → 触发抽取任务 → 变成 memories 里的 events / entities / preferences。

同一段对话，先作为会话记录留在 `sessions/` 里，再由抽取任务蒸馏成 `memories/` 下的条目。

sessions 是原始记录，memories 是二手结论，两者都在 user 作用域里，只是生命周期不同。

## 补充：隐藏文件

OpenViking 有三类核心隐藏文件，负责目录摘要与元数据：

| 文件名 | 内容 | 
|---|---|
| `.abstract.md` | L0 目录摘要，正文上限约 256 字符；检索时先读它 | 
| `.overview.md` | L1 目录概览，上限约 4000 字符；决定要不要进这个目录 | 
| `.meta.json` | 元数据，会话目录里记创建时间、来源等 | 

> `.abstract.md` 和 `.overview.md` 在各个目录中按需生成，不是每个目录都有；

> `.meta.json` 则只在会话目录 `viking://user/<id>/sessions/<session_id>/` 中存在。

除此之外还有几类按需出现、容易忽略的隐藏文件：会话目录的：

- `.recall_log.json`（这次会话召回了哪些上下文）；

以及 `history/archive_00N/` 下的：

- `.done` 与 `.failed.json`（归档队列的完成与失败标记）。

检索时的顺序是：

- 先读 L0 判断“这个目录跟问题有没有关系”，

- 再读 L1 判断“值不值得进去”，

- 进去之后才读 L2 原文。

这就是“分层检索”在存储侧的实现方式。

## 补充：身份与路径

### 四层结构

> 判断一个层算不算身份层，看两条（满足其一即可）：能否单独签发凭证，能否作为 ACL 的授权对象。

OpenViking 的目录可按照**权限 / 组织**划分为四层，如下所示——其中 Account 与 User 是身份层，Peer 与 Session 只是容器：

| 层 | 性质 | 鉴权主体 | 对应路径 |
|---|---|---|---|
| Account | 团队或组织（租户） | 是 | 无独立路径，由凭证确定；表现为 `viking://`：`resources`、`agent` 两支共享区 |
| User | 数据拥有者、鉴权身份 | 是 | `viking://user/<id>/`：memories、resources、skills、sessions、peers、privacy 六支 |
| Peer | User 空间内的记忆分区 | 否 | `viking://user/<id>/peers/<peer_id>/` |
| Session | User 空间内的数据容器 | 否 | `viking://user/<id>/sessions/<session_id>/` |

Peer 是 User 空间内的**稳定交互对象**；Session 是 User 空间内的一次**提交单元**。

> `sessions/` 是集合，`sessions/<session_id>/` 是集合里的元素；

> User 行给的是集合、Session 行给的是元素，两行路径看着嵌套，实际不是并列的层；

> `peers/` 也是同理。

值得一提，`sessions/` 里的 `session_id` 有两类前缀：

- `dsh-` 开头：DSH 插件按会话建的，后面跟会话 UUID。

- `mcp-store-` 开头：调用 MCP 工具 `remember` 时服务端合成的写入批次，后面跟 12 位哈希。

`mcp-store-` 开头的文件夹中没有存真实对话，只有 1–2 条消息、1 次提交，以及 0–N 条被提取出来的记忆。

所以 `sessions/` 装的不只是对话，而是所有走过**提交管线**的单元。

### 四种上下文类型针对不同身份的路径

| 内容类型 | Account 级（共享） | User 级 | Peer 级 |
|---|---|---|---|
| memory | 没有 Account 级路径 | `viking://user/<id>/memories/` | `viking://user/<id>/peers/<peer_id>/memories/` |
| resource | `viking://resources/` | `viking://user/<id>/resources/` | `viking://user/<id>/peers/<peer_id>/resources/` |
| skill | `viking://agent/skills/` | `viking://user/<id>/skills/` | 没有 peer 级路径 |
| rule（Beta） | 没有 Account 级路径 | `viking://user/<id>/memories/rules/` | 没有 peer 级路径 |

> 注意：`memories/skills/` 是**记忆的一种类型**（“技能执行经验”），和 `viking://user/<用户 ID>/skills/`（`SKILL.md` 技能包）是两码事。

规则和前三种不一样：它不是写进去的，是编译出来的，落在 `memories/rules/` 下、按账号与用户隔离，机制见第三章「其四」。

### peer 的两个角色

|角色	| 谁在设置	| 作用 |
|---|---|---|
| 记忆归着点 | 会话的 memory policy，以及会话声明的 `peer_id` | 会话抽取的记忆，写进 self 还是 peer |
|访问范围	| 请求里的 `actor_peer_id`	| 收窄“本次请求能看到哪些 peer 的内容” |

peer 不是**权限边界**。actor peer 只限制当前用户下的 peer 集合，用户自己的 self 记忆、自己的资料、以及有权访问的共享资料照旧可见；

而且持有完整 User Key 的客户端可以改变甚至省略这个范围；

总的来说，peer 是 **「组织」工具**，不是 **「安全」工具**。想隔离敏感数据，要用不同的 User 身份或 ACL。

### DSH 中的 peer

| 维度 | 原生语义 | DSH 插件的用法 |
| --- | --- | --- |
| peer 代表 | 对话的另一方：一个人或另一个 Agent | 一个工作目录或项目 |
| 谁决定 | 用户显式指定 `peer_id` | 插件按 git `origin` 或 cwd 自动推导 |
| 记忆按什么分 | 关于谁（self 与 peer） | 在哪个项目里说的 |
| 典型价值 | 给不同对象维护不同偏好 | 防止 A 项目的记忆串到 B 项目 |

在 DSH 中，一条记忆写在哪个空间，取决于**用户当时在哪个工作目录**：

- 目录是 git 仓库 → 用仓库 `origin` 归一化成 peer（同一个仓库的 clone / worktree / 子目录共用一个）；

- 目录不是 git 仓库，也没配置 → **不发送 peer，记忆落到用户级空间** `viking://user/<id>/memories`（全局共享）。

如果想手动让某个目录有独立记忆，在它下面放一个 `.openviking/config.json`：

```json
{ "version": 1, "peer": { "id": "cur_peer" } }
```

> `id` 这里填一个合法的 `peer_id`。

关于 `peer_id` 的一些补充：
- id 用 ASCII 单段、别带 `/`；
- 指定的 peer 只对新会话生效；
- 同名即同一抽屉（peer），换机器接着用就延续上下文。

## 补充：设置层与策略（0.5.4 新增）

0.5.4 把「东西放在哪、抽不抽、谁能看」从散落的 `ov.conf` 与命令行参数，收成三层可运行时修改的配置。它们不写进 `viking://`，却直接决定目录里长出什么。

| 层 | 接口 | 管什么 |
|---|---|---|
| Account | `GET` / `PATCH` `/api/v1/admin/accounts/{account_id}/settings` | `agent_evolution.enabled`、`acl.enabled` |
| Account | `GET` / `PATCH` `/api/v1/admin/accounts/{account_id}/configuration` | 抽取开关、生成语言、解析凭证 |
| User | `GET` / `PATCH` `/api/v1/admin/accounts/{account_id}/users/{user_id}/settings` | `add_targets`、`memory_policy`、`ttl` |
| User | `GET` / `PATCH` / `DELETE` `/api/v1/user-settings/add-locations` | 用户自己改 `resource_uri` / `skill_uri` 的覆盖值 |

本实例实测的取值：

- Account 层：`agent_evolution.enabled = false`、`acl.enabled = false`——与第三章「其三」说的「这条流水线默认是关的」一致，只是现在不用去翻 `ov.conf` 也能确认。

- User 层：`memory_policy.self.enabled = true`、`peer.enabled = true`、`working_memory.enabled = false`——self 记忆与 peer 记忆都抽，工作记忆不抽。

- User 层：`memory_policy.memory_types` 只列九类——`cases`、`entities`、`events`、`experiences`、`identity`、`preferences`、`profile`、`soul`、`trajectories`。`tools` 与 `skills` 虽然在模板里有对应文件，不在默认抽取清单内。

`add_targets` 回答的是「新导入的东西默认落哪」：`resource_uri` 与 `skill_uri` 现在都是 `null`，即跟随默认规则。这两项普通用户自己就能改，不必请管理员动 `ov.conf`——`/api/v1/user-settings/add-locations` 返回 `override` 与 `effective` 两份，能直接看出「我设了什么」和「实际生效的是什么」。

### 归档重试

失败归档不再只能等下一次提交：`POST /api/v1/sessions/{session_id}/archives/{archive_id}/retry` 可以对指定归档显式重试，重试请求带内容哈希，防止拿旧结果覆盖新内容。磁盘上对应的就是 `history/archive_00N/` 里的 `.failed.json`。

### 快照版本

`GET /api/v1/snapshot/versions` 与 `GET /api/v1/snapshot/diff-paths` 是 0.5.4 新加的两条只读接口：前者列版本，后者按路径看差异。`commit` / `restore` / `ignore` / `show` / `log` 等旧接口保持不变。
