# OpenViking 深入理解（上下文存储层）

## 序言

> date: 2026/11/11

由大肥鱼创作，我负责校对。目的是更细致地介绍 OpenViking 的理念、架构、功能和执行流程。

目前计划从五个层次理解 OpenViking 的内部架构，这是第一节：上下文存储层。在这个章节中，我们主要介绍四点：

- 介绍 OpenViking 的虚拟文件系统的全貌；

- 介绍四层结构；

- 介绍四种上下文类型；

- 介绍 OpenViking 双层存储的另一半：向量库。

## 总览

官方「上下文类型」把上下文分成四类：**Resource**、**Memory**、**Skill**、**Rule**。

但“上下文存储层”在实现上是另一套东西：

- AGFS 放正文，是本篇的重点讨论内容；

-  向量库放索引，它并不扩展语义，它的存在只是为了方便索引与检索。

`viking://` 是 OpenViking 给 AGFS 中的内容起的统一地址格式，官方称它为 Viking URI。

Viking URI 的格式为 `viking://{scope}/{path}`，`scope` 表示作用域，`path` 表示路径。

类型决定生命周期和由谁写入，存储结构决定权限和读取成本，两者不能互相替代。

## 第一章：四个作用域

`viking://` 下有四支：`user` / `resources` / `agent` / `system`。前三支的关系是“谁能看见”，最后一支回答的是“什么是内置的”。

### user 子目录

`viking://user/` 下都是按用户 ID 命名的目录，正如后续章节展示的那样，这些文件夹的内部结构是类似的。

### resources 子目录

`viking://resources/`：账号共享的资料区。

### agent 子目录

`viking://agent/`：在账号内共享的能力与配置目录，其子目录分别如下所示：

- `skills/`：共享技能；

- `tools/`：共享的 MCP 工具清单与实时节点；

- `endpoints/`：规划中，本实例为空；

- `payments/`：规划中，本实例为空；

> `viking://agent/` 没有 `memories`：官方明确说明记忆不使用独立的 `viking://agent/memories`，记忆只放在 user 或 peer 命名空间。

### system 子目录

`viking://system/`：只读作用域，装 OpenViking 自带的两类资产，不属于任何账号或用户：

- `compile/example-skills/`：供 `ov compile` 与 Studio 的「编排」「编译」使用，含四个示例技能：

  - `daily-report`，

  - `knowledge-distillation`，

  - `llm-wiki`，

  - `ov-session-report`。

- `memory/memory_templates/`：

  - `builtin/` 是 11 份内置记忆模板（`.yaml` 格式）；

  - 另有一个 `experimental_memory/` 目录；`custom/` 是唯一可写的位置。

`viking://system/` 在命名空间策略里被单独划出来：

- 不支持 ACL、不支持标签、不支持重建索引；

- 不进语义队列，不生成 `.abstract.md` / `.overview.md`，也不向量化。

换句话说，`system/` 里的文件能读、能当模板用，但永远不会变成检索结果。

固定目录本身不可写，只有 `memory_templates/custom/` 下的资产可以写。

写进去按 Account 生效，一个记忆类型一个文件（`<memory_type>.yaml`）。

## 第二章：六个固定子目录与 tools

`viking://user/<id>/` 除了 `tools/` 外的六个子目录是平台固定下来的。

`tools/` 则是由 MCP 服务在第一次注册或挂载工具时创建，没碰过 MCP 就完全不存在。

| 子目录	| 谁写入	| 装什么	| 
|---|---|---|
| `memories/` | 会话提交后的抽取任务 | 长期记忆；规则编译后另有 `rules/` |
| `resources/` |	你导入资料时	| 个人私有资料区 |
| `skills/` |	安装技能时	| `SKILL.md` 与配套脚本 |	
| `sessions/` | 每次对话由插件写入 |	消息流、工具结果、归档、召回日志	|
| `peers/` |	写入带 `peer_id` 的记忆或 peer 资料时 | 关于某个交互对象的记忆与资料 |	
| `privacy/` | 安装技能或登记密钥时 | 敏感配置的分版本快照 |
| `tools/` | OpenViking 自己（`mcps add` 写清单、`mcps mount` 写节点） | 用户私有的 MCP 工具清单与实时节点；按需创建 |

`memories/`、`skills/`、`tools/`、`resources/` 后文会详细讲，这个章节先讲其他的几个子目录。

### peers 子目录

`peers/` 中的文件夹按 `peer_id` 命名，每个 `viking://user/<id>/peers/<peer_id>/` 下只有两个位置：

| 位置	| 装什么	| 什么时候出现 |
|---|---|---|
| `viking://user/<id>/peers/<peer_id>/memories/` | 关于这个对象的记忆，子结构与用户根同源 | 首次抽取写入时 |
| `viking://user/<id>/peers/<peer_id>/resources/` | 与这个对象相关的资料 | 只有人往里放资料时 |

所以 peer 下没有 `sessions/`、`skills/`、`privacy/`——这三个只属于 user 空间。

`memories/` 的结构跟用户根基本一致——同一套记忆模板，只把 `{{ user_space }}` 从 `<id>` 换成 `<id>/peers/<peer_id>`。

区别只在能落进来的类型：

- `profile.md` 记的是这个对象的长期状态，不是用户画像；一个 `profile.md` 里可以有多名参与者，每人一个 H1；

- `preferences/`、`entities/`、`events/` 的语义同样以该 peer 为主体；

- `cases/`、`trajectories/`、`experiences/` 只有 user 根会有，peer 下永远不会存在；

- `rules/` 只有 user 的 `memories/` 会有，peer 的 `memories/` 中不会有；

- `identity` 与 `soul` 描述助手自身，几乎不会挂到某个 peer 下。

### sessions 子目录

`sessions/` 中的文件夹按 `session_id` 命名，每个 `sessions/<session_id>/` 的结构是：

- `messages.jsonl`（消息流）

- `history/`（归档）
  
- `tool-results/`（有工具调用时才出现）

- `.recall_log.json`（这次会话召回了哪些上下文）

值得一提，`sessions/` 里的 `session_id` 有两类前缀：

- `dsh-` 开头：DSH 插件按会话建的，后面跟会话 UUID。

- `mcp-store-` 开头：调用 MCP 工具 `remember` 时服务端合成的写入批次，后面跟 12 位哈希。

### privacy 子目录

privacy 子目录解决一个很具体的问题：API key、PAT、密码这类字符串，不该出现在记忆、会话归档、向量库和日志里。

目录按 `privacy/<category>/<target_key>/` 组织，一个 `target_key` 一个目录，其中含有以下文件：

- `current.json`——当前生效的那份值

- `.meta.json`——版本等元信息

- `history/version_001.json`、`history/version_002.json`——每次改动留一份，旧值不覆盖

这是"分版本快照"的实际含义：**改一次值多一个版本文件，`current.json` 指向生效的那份**，历史可以回溯。

category 目前有三类，差别只在"值从哪来"：

| category	| 值从哪来	| 备注	|
|---|---|---|
| `skill` | 安装技能时从技能文件里自动抽取 | 技能声明的字段 |
| `credential` | 人手动登记 | 如 `github` 的 PAT |
| `session` | 会话内容替换 | 新值自动探测目前被官方暂时禁用 |

## 第三章：memories 内部按类型分家

`viking://user/<id>/memories/` 下能出现三样东西：

- **11 个记忆类型**：8 个目录型，3 个文件型。它们由记忆模板登记，可以扩展或调整。

- **1 个预留目录** `patterns/`：有目录定义，没有模板，不算记忆类型。

- **1 个非记忆位置** `rules/`：规则（Rule，Beta）的落点，不在类型表里。

这 11 个都归在 memory 这一类上下文里；resource、skill、rule 不再按类型细分。

记忆类型由模板决定，模板能改；目录名不能改。

| 记忆类型	| 落点	| 装什么	| 默认	|
|---|---|---|---|
| preferences	| `memories/preferences/`	| 按主题组织的偏好	| 启用 |
| entities	| `memories/entities/`	| 人、项目、工具等实体知识	| 启用 |
| events	| `memories/events/<年>/<月>/<日>/`	| 决策、里程碑、发生过什么	| 启用 |
| cases	| `memories/cases/`	| 任务案例：目标、步骤、结果	| 启用（需 Agent 演进） |
| trajectories	| `memories/trajectories/`	| 可复用的执行轨迹	| 启用（需 Agent 演进） |
| experiences	| `memories/experiences/`	| 从执行结果提炼的经验	| 启用（需 Agent 演进） |
| profile	| `memories/profile.md`	| 你是谁：身份、职业、关系	| 启用 |
| identity	| `memories/identity.md`	| 助手自己的名字、形象、自我介绍	| 启用 |
| soul	| `memories/soul.md`	| 助手的核心原则与边界	| 启用 |
| skills	| `memories/skills/`	| 关于技能使用的记忆	| **模板存在，`enabled: false`** |
| tools	| `memories/tools/`	| 关于工具调用的记忆	| **模板存在，`enabled: false`** |

`memories/rules/` 里放的是规则（Rule，Beta）。它连目录定义都没有，是规则编译器在第一次编译时现建的。

`memories/patterns/` 和上述记忆类型不一样，见本章最后一节。

### identity & soul

`identity.md` 与 `soul.md` 并不是关于“用户”的画像，而是助手自己的自我设定。

- `identity.md` 里是待填的 Name / Creature / Vibe 字段；

- `soul.md` 里是 “Be helpful, not performative” 这类原则。

这跟“记住用户”是两件事。

### entities & events

`entities` 和 `events` 都再分了子目录，这也是它们看起来最“乱”的原因：

- **`entities`** 按主题（比如：人物、学术论文、工具、开源项目、教材_讲义、文档、概念、系统等，都是根据实际对话归纳的）。
  
- **`events`** 按事件发生日期分年/月/日，如 `memories/events/2026/11/09/`。

### cases & trajectories & experiences

`cases`、`trajectories`、`experiences` 是成组出现的，也是上表里唯一一组带有「训练」环节的记忆。

它们归在「Agent 演进」这条流水线下，彼此有前后依赖，不是三个并列的目录。

只有产出 `case` 后，才会继续训练 `trajectories` 与 `experiences`；没有 `case`，另外两个目录不会自己长东西。

### patterns

`patterns` 目前是个**预留位置**：

- 目录定义先到位（`core/directories.py` 里有 `path="patterns"`），但内置模板集里没有 `patterns.yaml`。

- 没有模板就不算记忆类型——抽取器不会产出它，把它写进 `memory_policy.memory_types` 也会被判成未知类型。

## 第四章：两则补充

### tools（补充第一、二章）

它是 MCP 工具的落点，分两样东西：

- **清单**：`mcps add` 时批量写入。

  - 一个工具一个 `<server>/<tool>.json`，装的是名称、描述、参数定义。`sync` 会跟随上游改动重写。

- **节点**：`mcps mount` 时写入。

  - 路径由调用方指定，内容带 `x-openviking` 元数据（调用定义、参数、超时、重试）。读它一次，等于调一次工具。

写入的永远是 OpenViking 服务端自己，外部 MCP 服务器只提供清单和结果，从不碰这个目录。

tools 默认落在**用户私有**根（`viking://user/<id>/tools`）；要账号共享，得显式指定 `viking://agent/tools`。

tools 目录按需创建：第一次 `add` 才建出来，所以没注册过 MCP 的实例里根本没有这一层。

tools **没有对应的上下文类型**。它**不参与检索**，只能按路径 `ls`、`read`、`glob` 取，`find` / `search` 不会返回它。

### 重要隐藏文件（补充第一、二、三、四章）

OpenViking 有三类重要隐藏文件，负责目录摘要与元数据：

| 文件名 | 内容 | 
|---|---|
| `.abstract.md` | L0 目录摘要，正文上限约 256 字符；检索时先读它 | 
| `.overview.md` | L1 目录概览，上限约 4000 字符；决定要不要进这个目录 | 
| `.meta.json` | 元数据：会话里记 id、时间戳、提交次数、各类记忆抽取数量与 token 统计；`privacy` 里记版本 | 

> `.abstract.md` 和 `.overview.md` 在各个目录中按需生成，不是每个目录都有；

> `.meta.json` 出现在三处：`sessions/<session_id>/`、`history/archive_00N/`、`privacy/<category>/<target_key>/`。

## 第五章：身份与路径

### 四层结构

OpenViking 的目录可按照**权限 / 组织**划分为四层，如下所示——其中 Account 与 User 是身份层，Peer 与 Session 只是容器：

| 层 | 性质 | 鉴权主体 | 对应路径 |
|---|---|---|---|
| Account | 团队或组织（租户） | 是 | 无独立路径，由凭证确定；表现为 `viking://` 下的 `resources`、`agent` 两支共享区 |
| User | 数据拥有者、鉴权身份 | 是 | `viking://user/<id>/`：固定的六支，以及按需创建的 tools |
| Peer | User 空间内的记忆分区 | 否 | `viking://user/<id>/peers/<peer_id>/` |
| Session | User 空间内的数据容器 | 否 | `viking://user/<id>/sessions/<session_id>/` |

### 四种上下文类型针对不同身份的路径

| 内容类型 | Account 级（共享） | User 级 | Peer 级 |
|---|---|---|---|
| memory | 没有 Account 级路径 | `viking://user/<id>/memories/` | `viking://user/<id>/peers/<peer_id>/memories/` |
| resource | `viking://resources/` | `viking://user/<id>/resources/` | `viking://user/<id>/peers/<peer_id>/resources/` |
| skill | `viking://agent/skills/` | `viking://user/<id>/skills/` | 没有 peer 级路径 |
| rule | 没有 Account 级路径 | `viking://user/<id>/memories/rules/` | 没有 peer 级路径 |

## 第六章：上下文

官方四类上下文落到 `viking://` 上，各有各的落点与写法。

### Memories 记忆

每条记忆是一个 `.md` 文件，正文之后跟一段 `<!-- MEMORY_FIELDS {...} -->` 注释，记录 `memory_type`、版本、来源抽取 id 等字段。

记忆的类型与落点，在介绍虚拟文件系统时已经讲过（详见第三章）。

每个目录中放什么、叫什么名字由**记忆模板**决定：

- 模板给出 `directory` 与 `filename_template`；

- 所以"增加一种记忆类型"是加一份模板，不是新建目录——这也是第三章那张表能扩展的原因。

记忆的生命周期按类型分以下几种：

- `events` 是历史记录，写下不再改；

- `preferences`、`entities`、`profile` 这类会被后续抽取 upsert 覆盖；

- `cases`、`trajectories`、`experiences` 由 Agent 演进功能决定，默认不产出。

### Resources 资源

一条资源是**一个目录**，不是单个文件；一个资源目录里可能有多份文件（一份文档连同它的图片、附件），它们算同一个资源。

资源是**快照**：导入那一刻固定下来，之后外部源变化不会自动跟进；要更新就重新导入一次，覆盖原来那份。

资源完整支持三项能力：ACL（按目录授权）、标签（按标签过滤）、重建索引。

### Skills 技能

技能在磁盘上就是一个普通目录，目录名就是技能名，只允许字母、数字、下划线和短横，沿用 Claude Skills 规范对技能目录的约定。

| 文件	| 必需	| 装什么	|
|---|---|---|
| `SKILL.md` | 是	| YAML frontmatter + 正文（"怎么做"的说明书） |
| `.source.json` | 否	| 从 Git 仓库、本地目录或 zip 安装时记下的来源（`clone_url`、`ref`、`subdir`） |
| 其他文件 | 否	| 脚本、参考资料、素材，按原相对路径落盘 |

在 `SKILL.md` 文件内部，需要注意以下几点：

- frontmatter 至少要有 `name` 和 `description`，

- `allowed-tools`（空格分隔的工具白名单）、`tags`（检索用）、`metadata` 是可选的。

- 分隔符 `---` 之后才是正文。

结构上还有两条：

- **扁平存放**。技能直接并列在 `skills/` 下，不按分类再建一级子目录；分类靠 frontmatter 里的 `tags`，不靠路径。

- **一个技能是一个目录**，所以删除是整目录删除（`DELETE /api/v1/skills/{name}`），不会留下半份文件。

### Rules 规则

规则只是「借位」存放：位置在 `memories/` 下，读写却走独立的编译与搜索接口。

- 代码里也没有为规则单列类型：`ContextType` 只有 `SKILL`、`MEMORY`、`RESOURCE` 三个值，`memories/rules/` 按路径会被判成 memory。

编译是指从一条指令或一批资料里提炼强约束，落成 `memories/rules/<scenario>/` 下具体的规则文件。

`memories/rules/<scenario>/` 里是若干条规则文件 `<atomic_id>.md`，外加 `abstract.md`（L0），但没有 `overview.md`（L1）。

规则有三种状态 `active`、`paused`、`archived`——暂停的仍可被重新编译覆盖，但不再参与召回；归档是逻辑删除，保留期默认 30 天。

它跟记忆的生命周期刚好相反：

- 记忆是抽出来的、会不断被 upsert；

- 规则是编译一次、由人启停。

## 第七章：向量库

### 文件系统之外

OpenViking 是**双层存储**：一套放正文，一套放索引。

| 层 | 存什么 | 
|---|---|---|
| AGFS | 正文、附件、多媒体原文件 | 
| 向量库 | URI、向量、元数据、摘要文本 | 

前六章讲的都是前一层：目录怎么分、谁写哪一支、隐藏文件放在哪。

这一章讲后一层——它不生产内容，只让内容变得**可被找到**。

### 不产生语义，只产生可检索性

文件系统按路径组织，检索按相似度组织，这两件事天然不是一棵树。

- 路径是**定位**：知道在哪，就能一次读到；

- 向量是**比较**：不知道在哪，也能找到「意思接近」的那几条。

把两者塞进一套存储，要么牺牲顺序读，要么牺牲近似最近邻。所以 OpenViking 分成两层：AGFS 保证「读得到」，向量库保证「搜得着」。

> 两层的状态允许短暂不一致。文件先落盘、摘要与向量后补，这中间存在「文件在、搜不到」的窗口。

### 向量库中的记录

一条记录是**一个可以被独立命中的片段**，不是一份文件。

粒度沿用 L0 / L1 / L2：目录摘要、目录概览、文件正文各算一条记录。

一条记录大致由七组字段构成：

| 职责 | 字段 | 说明 |
|---|---|---|
| 身份 | `id`、`uri`、`parent_uri` | 记录落回哪个路径；`id` 由账号与路径派生，可以离线复算 |
| 粒度 | `level` | 0 / 1 / 2，标明这条代表目录摘要还是正文 |
| 类型 | `context_type` | resource / memory / skill，决定摘要从哪来、走哪条检索通道，rule 算在 memory 里 |
| 文本 | `abstract`、`content` | `abstract` 供展示与重排；`content` 供词法检索（BM25） |
| 向量 | `vector`、`sparse_vector` | 密集向量管语义相近，稀疏向量管关键词命中 |
| 过滤 | 标签、时间、使用次数 | 检索时先按它们筛掉一批，再算相似度 |
| 归属 | 账号、用户、ACL | 决定「谁能看见」，见下节 |

> 主要的字段大致如上表所示，但实际会因为向量库的后端实现不同而有一定差异。

### 正文怎么变成记录

一条链路：解析 → 摘要 → 选文 → embedding → 写入。

关键在「选文」——**进向量库的文本不等于原文件**：

- 资源：L0 / L1 是摘要；L2 的 `abstract` 是语义摘要，`content` 才是解析后的原文；
- 记忆：正文直接进 `abstract`，所以记忆的正文在向量库里也能读到；
- 技能：目录级摘要来自 `SKILL.md` 的元数据，正文来自技能文档本身。

这也是「搜到一条结果为什么只有一段话」的答案：命中的是记录，不是文件。要读全文，还得拿 `uri` 回 AGFS 取。

### 集合、索引、后端

这三个词经常混在一起，其实是三层：

| 层次 | 是什么 | 由谁决定 |
|---|---|---|
| 集合 collection | 一类上下文的逻辑表 | 产品固定，OpenViking 把各类上下文统一放进一个集合 |
| 索引 index | 一套参数：距离度量、近似算法、量化方式 | 部署时配置，可重建 |
| 后端 backend | 实际存算的地方 | 部署时选择 |

两点值得记住：

- **多租户靠字段，不靠多集合**。所有账号共用一套索引，查询时用记录上的账号与 ACL 过滤。好处是升级只做一次、参数只需调一套；代价是过滤必须可靠，漏一个条件就是越权。

- **索引参数只影响速度与召回，不影响内容**。同一批记录换个索引，重扫一遍即可，不必重新解析文件。

后端可以换：嵌入式本地、远程 HTTP 服务、云上的向量数据库，对上层接口一致，能力有差别（是否支持稀疏、量化、标量过滤）。

### 和文件树怎么保持一致

写向量是异步的：文件先落盘，摘要与向量后补。为了让两边不越走越远，文件系统操作会顺手同步索引：

- **删除**：按 URI 前缀把对应记录一并删掉；
- **移动**：改记录里的 `uri` 与 `parent_uri`；
- **覆盖导入**：比对内容摘要（如 md5），只重算变化的部分。

> 同步不是事务性的。官方文档明确说目录摘要可能继续异步刷新，失败也可能留下部分变更。「文件删了、记录还在」是会出现的中间态。

兜底手段是**重建索引**：从 AGFS 重新扫一遍，按当前配置重新生成摘要与向量，整体覆盖。它也是换 embedding 模型时唯一正确的做法——维度与语义空间都变了，旧向量不能混用。

### 它不负责什么

- **不做鉴权裁决**。记录上的 ACL 是检索时的过滤条件，真正的权限判断在服务端入口；
- **不做召回策略**。捞几条、给多长、怎么拼成上下文，是下一层的事；
- **不存正文**。正文永远在 AGFS，向量库里只有摘要与引用（记忆是例外，正文就存在 `abstract` 里）。

### 本章边界

- 记录长什么样、检索怎么用它：见《索引与检索层》；
- 向量与摘要怎么算出来：见《语义处理层》；
- 本章只回答「另一半为什么存在、由什么构成、和文件怎么同步」。
