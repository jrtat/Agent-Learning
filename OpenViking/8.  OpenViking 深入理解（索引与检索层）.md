## 序言

> date: 2026/11/10

由大肥鱼创作，我负责校对。

目的是更细致地介绍 OpenViking 的理念、架构、功能和执行流程。

目前计划从五个层次理解 OpenViking 的内部架构，这是第四节：索引与检索层。

在这个章节中，我们将看一句话怎么变成「模型眼前的一段上下文」。

## 总览

语义处理层交出来两样东西：能比的向量、能用的摘要。但这两样东西本身不会自己跑到模型面前。中间还差一层：

- **写侧（索引）**：什么东西以什么粒度进了向量库，一条记录带哪些字段；

- **读侧（检索）**：一句话进来，用哪条路径捞，捞几条，每条给多长，最后拼成什么形状。

| 维度 | 索引（写侧） | 检索（读侧） |
|---|---|---|
| 处理对象 | 目录 L0、目录 L1、文件 L2 | 查询句、会话、正则、路径 |
| 产出 | 向量记录 + 摘要 + 标签 | 命中列表，或组装好的上下文块 |
| 时机 | 异步，跟在写入后面 | 同步，卡在对话中间 |
| 失败表现 | 搜不到（索引没建完） | 搜到但不相关 / 太多 / 太少 |

开篇先纠正一个容易过时的印象：**OpenViking 的语义检索不是「从根目录一层层往下翻」。** 

最新文档写得很直白：「未指定 `level` 时，文本查询可直接命中 L0/L1/L2；不再先定位目录再逐层搜索」。

这一点很重要，因为它改变了你对结果的预期：

- 命中可能是文件、可能是目录摘要、也可能是技能包，它们平铺在同一张候选表里比较分数，没有「先目录后文件」的层级顺序。

## 第一章：索引——什么进了向量库

检索的天花板由索引决定。索引里没有的东西，检索再调也捞不出来。

### 三种粒度

| 层级 | 落在哪 | 内容 | 默认长度 |
|---|---|---|---|
| L0 | 目录下的 `.abstract.md` | 这个目录一句话讲什么 | 256 字符（`semantic.abstract_max_chars`） |
| L1 | 目录下的 `.overview.md` | 这个目录里有什么、怎么组织 | 4000 字符（`semantic.overview_max_chars`） |
| L2 | 文件本身 | 正文，或记忆文件的全文 | 按文件 |

一条向量记录就是一个「*可以被独立命中的片段*」。所以：

- 一个目录至少两条记录（L0 和 L1），不是一条；

- 一个文件一条（当前版本的 memory 直接用原文件的 L2，不再生成虚拟 `#chunk_NNNN` 记录）。

这解释了两个日常现象。同一个目录可能同时以 `.abstract.md` 和 `.overview.md` 两个条目出现在结果里；

「命中了一个目录」也不等于「命中了它下面的任何文件」——目录摘要只是一段关于目录的概括文字，跟子文件内容是两回事。

### 向量记录里有什么

| 字段 | 作用 |
|---|---|
| `uri` | 地址，结果的唯一落点 |
| `level` | 0 / 1 / 2，决定后续用哪个接口读 |
| `abstract` | 展示用的摘要，也是 Rerank 的输入文本 |
| `content` | 正文，仅 VikingDB 系后端写入，供 BM25 用，截断到 1 MB |
| `tags` | 检索标签，两种来源，见下 |
| `updated_at` | 时间过滤与事件衰减的基准 |
| `id` | 仅 L2 文件有，`md5(account_id:uri)`，确定性主键 |

`id` 这一条有两个直接后果。同一个文件在任何时候算出来的 id 都一样，可以拿它反查向量记录；目录没有这个字段，因为一个目录对应多条记录（L0、L1），主键不唯一。

标签有两种，别混：

- **记忆类型标签**：记忆抽取时自动写入的 `memory_type=events` 这类，用于分桶和时间衰减；

- **显式检索标签**：你自己用 `set_tags` 或写入时的 `tags` 参数打的 `k=v`，多个之间是 AND，检索时当过滤器用。

### 不该进向量的，确实没进

目录 L0/L1 进向量时只带一个白名单字段 `directory`；`source`、`generated_by`、`freshness` 这些元数据都不进。

上一篇从「重建索引分数要稳定」的角度讲过这条，这里补上检索侧的后果：**分数只反映内容像不像，不反映新旧、来源和重要度**。

一条三年前的记忆和一条昨天的记忆，只要语义接近，向量分可以完全一样。

这不是缺陷，是分工——「新不新」交给时间过滤和事件衰减，「重不重要」交给预算和配额。

### 索引是异步的，检索是即时的

写入接口返回成功，只代表正文落盘；向量还在队列里。`stat(id)` 在这段时间会返回 `NOT_FOUND`，并提示「可能尚未索引或已经删除」。

所以「刚导入就问为什么搜不到」的标准排查顺序是：看任务中心的任务状态 → 必要时 `reindex` → 最后才怀疑阈值。

`reindex` 做的是三件事：补缺失或过期的记录、删内容已不存在的孤儿向量、跳过状态一致的记录。它不会重建整个集合。
