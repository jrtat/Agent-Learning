# OpenViking 深入理解（数据接入层）

## 序言

> date: 2026/11/8

由大肥鱼创作，我负责校对。

目的是更细致地介绍 OpenViking 的理念、架构、功能和执行流程。

目前计划从五个层次理解 OpenViking 的内部架构，这是第二节：数据接入层。

在这个章节中，我们将知道存储在 OpenViking 中的数据都是怎么来的。

## 总览

所有数据只有三条**进入**路径，第四条是**编译**出来的：

| 入口 | 典型动作 | 落点 |
|---|---|---|
| 对话 | DSH 里聊天，插件自动捕获 | `viking://user/<id>/sessions/` → 蒸馏进 `memories/` |
| 资源 | 导入文件、URL、Git 仓库 | `viking://resources/` 或 `viking://user/<id>/resources/` |
| 技能 | 安装 `SKILL.md` | `viking://user/<id>/skills/<name>/` 或 `viking://agent/skills/` |
| 规则 | 编译指令或已有资料 | `viking://user/<id>/memories/rules/` |

前三条最后都汇进同一条流水线：**解析 → 建树 → 落盘 → 语义处理 → 向量化**，差别只在前半段怎么把内容拿到手。

需要注意，三条进入路径和编译并没有严格对应四类上下文，这是因为**没有「直接写记忆」的接口**：

- 除了手动改 `memories/` 下的 md 文件，任何一条记忆都要先变成一个会话提交，再从会话里抽出来。

- 调用 `remember` 工具也一样——它仍然要经由一个特殊会话才能进入记忆（正如在《OpenViking 深入理解（上下文存储层）》中所述）。

## 第一章：对话怎么进来

这条路径最隐蔽，因为它对用户完全透明。

### 捕获三种消息，跳过一类内容

插件是跑在 DSH 进程内的 Cordis 插件，不是外挂钩子，所以能贴着会话的事件流走。

它捕获三种消息：**用户**、**助手**，以及（DSH 上默认开启的）**工具结果**。

> 每个会话里的消息分三类角色：user（用户发的）、assistant（模型答的）、tool（工具返回的）。

它跳过一类内容：DSH 或其他插件注入的上下文，例如时间注入、任务通知。

> 工具结果是个特例：**会被记录，随 commit 归档，但不参与召回**。

> 召回只用用户这一句里的文本做语义检索，工具结果既不触发召回，也不拼进检索文本。

> 换句话说，工具结果只影响「会话里存了什么」，不影响「下一次会话召回了什么」。

### 用 commit 实现落库

插件捕获到消息后不是立刻落库，而是攒到一个 commit。commit 有三个触发点：

- 待同步 token 超过阈值（插件默认 20000）；

- DSH 开始压缩上下文；

- 会话 teardown。

commit 一旦触发，就把**全部**已捕获的消息落库，所以一个 commit 里往往包含好几轮对话。

### 会话与路径的对应关系

每个 DSH 会话对应一个唯一的 `dsh-<session_id>` 目录，子 agent 各自独立，所以会话数量通常比人以为的多。

`remember` 工具是个例外。MCP 代理每个 profile 只起一个进程，拿不到「当前是哪个会话」。

所以 `remember` 工具写的是服务端临时合成的一个短会话，也就是 `mcp-store-<hash>`。

用户看到的是「记住了一件事」，实际发生的是「新建一个会话、塞进 1–2 条消息、提交、抽取」。

## 第二章：资料怎么进来

### 落库流程总览

资料走的是完整四阶段，前三个阶段同步完成，第四个异步。

| 阶段 | 做什么 | 是否同步 |
|---|---|---|
| Parse | 按格式调解析器，产物先写临时目录 | 同步 |
| TreeBuilder | 确定最终 URI，处理同名冲突 | 同步 |
| Persist | 落盘、加路径锁、清理临时目录 | 同步 |
| Semantic | 进**语义队列**，生成 L0/L1 摘要，再把文件与目录的向量排进 Embedding 队列 | 异步，看 `task_id` |

### 五种格式

支持的格式可以归成五族：

- 文档：PDF、Markdown、HTML、Word、纯文本、EPUB；

- 表格与幻灯片：Excel、CSV、PowerPoint；

- 代码：常见语言源码、Git 仓库、GitHub 等平台的仓库地址；

- 媒体：图片、音视频（只做原文件校验与保存，内容理解默认关闭）；

- 云文档与网页：飞书、单页抓取、整站抓取。

### 三种进法

三种进法，代价不同：

- URL：服务端去抓，抓完即快照；

- 本地文件：先上传换 `temp_file_id` 再导入，**一次性快照**；

- Git：clone 后按 `.gitignore` 过滤，除了解析还要等 clone。

### 三个导入参数：`processing_mode`、`parse_mode` 与 `watch_interval` 

三个参数决定这次导入的形态。

- `processing_mode`：

  - `semantic_and_vectors`（默认，生成 `.abstract.md` 与 `.overview.md` 并向量化）

  - `vectors_only`（只向量化，跳过摘要）。

- `parse_mode`：

  - `default`（按标题和 2000 字符切分）

  - `no_split`（一个源文档只产出一个 Markdown）。

- `watch_interval`：大于 0 时会建定时任务，到期重新导入。但 `temp_file_id` 这种快照不支持定时更新。

### 两种落点：`to` 与 `parent`

- `to` 是覆盖，目标已存在就替换，目录里本次没生成的旧文件会被删掉；

- `parent` 是追加，父目录不存在时配合 `create_parent` 自动创建。

两者互斥，不能同时写。

### 一个记忆字段：`reason`

- 当 `reason` 字段非空时，服务端会把「这次导入的原因 + 资源 URI」送进常规的记忆抽取链路。

  - 此时记忆里会带上 `resource_refs`，日后删资源时能顺着它清理引用。

  - 这条链路只读 reason 和目录摘要，不展开资源正文。

## 第三章：技能与规则怎么进来

### 技能落库

`add_skill` 接收一份 `SKILL.md` （或 Git 地址、本地目录、zip），写到 `skills/<name>/SKILL.md`，然后和资料一样进**语义队列**。

装好的技能不会执行任何代码：它本身只是一段文本，会话开始时会被列进技能清单。

### 规则落库

规则走另一条路：不是写进去的，是编译出来的。

`POST /api/v1/rules/compile` 从一条指令或已有资料生成 Markdown，落在 `memories/rules/` 下。

它借用记忆的目录位置，身份却是规则——所以不出现在记忆类型表里。

## 第四章：由会话生成记忆

### 记忆提取

**记忆管线**相对于其他类型的上下文，在这段之前多一步：会话压缩 → 提取循环 → 记忆更新器。

- 压缩是把 `messages.jsonl` 里那堆原始消息整成可抽取的形态；

- 提取循环按**记忆类型**（profile、preferences、entities、events、cases……）逐类去问「这段对话里有没有这类信息」。

- 更新器决定新建一个 md 还是合并进已有条目。

### case 抽取

这里有个门槛：先抽 case，只有本次真的产出了至少一个 case，才会继续生成 `trajectories` 与 `experiences`（这两类记忆比较特殊）。

原因是这两类是「任务执行」的产物：

- 轨迹（trajectory）是「这类任务怎么一步步做的」。

- 经验（experience）是「做完之后总结出什么」。

没有可复用的任务案例，就没有可提炼的对象。

## 第五章：共用的后半程

### 语义队列

**语义队列**要做的是给每个目录配一句摘要（L0）、一段概览（L1），让检索时能先看目录再决定进不进去。

- 资源、记忆、技能这三类内容的摘要（L0）与（L1）都经由**语义队列**产生；规则是另一条路，它只有 Compiler 写进去的 abstract.md，不经过**语义队列**。

- 它只能从下往上跑（叶子目录 → 父目录 → 根目录），因为父目录的概览是拿子目录的摘要拼出来的。子目录还没摘要，父目录就没材料。

### 生成摘要和概览

每层做的四件事，其实是「汇集材料 → 写概览 → 压成一句」：

1. 给本目录下的每个文件并发生成一句摘要——这些摘要只用于凑材料，不会存成文件；

2. 收集各子目录的 .abstract.md，这是上一层已经写好的那一句；

3. 把这些材料交给模型，写成 .overview.md，上限约 4000 字符；

4. 再从这份 overview 里提取出 .abstract.md，压到约 256 字符。

以下是两个容易误解的点：

- L0/L1 是**目录级**的附属文件（sidecar），不是每个文件一份。文件内容直接进向量，没有自己的摘要文件。

- 生成父目录摘要时只读子目录的 L0 正文，那几行 `source:、generated_by:、freshness:` 不进 prompt，所以这类元数据不会污染摘要。

父级刷新还有一道 **freshness 判断**：子目录 L0 正文没变，就不向上传播，避免上层摘要无谓地重写。
