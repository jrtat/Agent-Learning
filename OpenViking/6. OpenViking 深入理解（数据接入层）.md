# OpenViking 深入理解（数据接入层）

## 序言

> date: 2026/11/11

由大肥鱼创作，我负责校对。目的是更细致地介绍 OpenViking 的理念、架构、功能和执行流程。

目前计划从五个层次理解 OpenViking 的内部架构，这是第二节：数据接入层。

这一篇只回答一个问题：**数据怎么从外部进入 OpenViking 的文件系统**：

- 从哪个口进来、进门时被拆成什么、写到哪一步算交接完成。

进来之后怎么被摘要、怎么被向量化、怎么被抽成记忆，本篇只在参数含义处点到为止。

## 总览

外部数据有四条**进入**路径：

| 入口 | 典型动作 |
|---|---|
| 对话 | DSH 里聊天，插件自动捕获并逐条写入 |
| 资源 | 导入文件、URL、Git 仓库、云文档、整站 |
| 技能 | 安装 `SKILL.md`、目录、zip、Git 来源 |
| 实时上下文 | 注册 MCP 服务器，把工具挂成节点 |

对话、资源、技能是「搬内容」：把外面的东西拿到文件系统里存一份副本，所以是**快照**——源变了不会自动跟着变，要重新导入。

实时上下文是「登记地址」：不搬正文，只在文件系统里挂一个节点（**引用**），读的时候才去调工具。

> 所以「接入」在这里有两层意思：把东西搬进来（前三），和在文件系统里造一个入口（后一）。

> 共同点是**最后都要占一个 `viking://` 路径**。

四条线都会经过下面四步，差别在第 1 步和第 4 步的处理轻重：

1. 内容先变成可读文本——文档类转 Markdown，本来就是文本的（对话、技能）原样收下，媒体只保留原文件；

2. 在 `viking://` 里确定一个地址，建目录树，URI 冲突自动改名；

3. 正文写进 AGFS（内容存储层）；

4. 把「写摘要、算向量」这类任务排进队列，默认不等它跑完。

第 4 步之后发生的一切，都在「已经落盘」之后，不在本篇的范围内。

## 第一章：以会话形式接入

会话形式接入的内容主要是作为记忆上下文，但也可以通过会话上传资源和技能等上下文。

### 捕获三种消息，跳过一类内容

以 OpenViking 接入 DSH 为例。跑在 DSH 进程内的 Cordis 插件捕获三种消息：

- **用户**（用户发的内容）；

- **助手**（模型答的内容）；

- **工具结果**（工具返回的）。

工具结果捕获在 DSH 上默认开启。

> 每个会话里的消息分三类角色：user、assistant、tool。

插件跳过一类内容：DSH 或其他插件注入的上下文，例如时间注入、任务通知、召回块、profile 块。

每个 DSH 会话对应一个唯一的 `dsh-session-<session_id>` 目录，子 agent 各自独立，所以会话数量通常比人以为的多。

### 用 commit 实现归档

消息本身是**逐条即时写入**的，所以会话目录里的消息会随着对话变长。

commit 决定的不是「消息什么时候进来」，而是「这一批消息什么时候被归档、可以交给后面处理」。commit 有三个自动触发点：

- 每轮对话结束时，插件数一下还有多少内容没归档，攒够 2 万 token 就提交；

- DSH 开始压缩上下文时无条件提交——压缩会重写历史，不提交就丢了；

- 会话 teardown 时再提交一次，把这次会话剩下的消息一并归档。

commit 一旦触发，就把当前全部未归档消息写成一个 archive，交给后续的语义处理。

> 服务端另有独立的自动提交策略（`auto_commit_policy`），用更大的阈值兜底那些插件管不到的会话。

### remember 工具的特殊 commit

`remember` 工具会提交一种特殊的会话。

由于 MCP 代理每个 profile 只起一个进程，拿不到「当前是哪个会话」。

所以 `remember` 工具写的是服务端临时合成的一个短会话，与 DSH 会话不同，其目录的命名格式为 `mcp-store-<hash>`。

用户看到的是「记住了一件事」，实际发生的是「新建一个会话、塞进 1–2 条消息、提交」。

## 第二章：以资源形式接入

资源形式接入后主要作为资源这一上下文类型。

### 六族格式

支持的格式可以归成六族：

| 族 | 典型格式 |
|---|---|
| 文档 | PDF、Markdown、HTML、Word、纯文本、EPUB |
| 表格与幻灯片 | Excel、CSV、PowerPoint |
| 代码与仓库 | 常见语言源码、`git://`、本地目录、zip、GitHub / GitLab / Bitbucket 仓库地址、平台上的 raw 文件地址 |
| 媒体 | 图片、音视频 |
| 云文档 | 飞书 doc / docx / wiki / sheets / bitable / mindnote、Drive 文件与目录集合 |
| 网页与整站 | 单页、递归抓取、sitemap / RSS / Atom、`args.site=true` 自动发现 |

以下是一些细节备注：

| 族 | 备注 |
|---|---|
| 文档 | PDF 可本地解析，也可走 MinerU API；HTML 转 Markdown；Word 与 EPUB 用 anydoc 抽正文、标题、表格与图片 |
| 表格与幻灯片 | 工作表与每页幻灯片都转成 Markdown |
| 代码与仓库 | clone 后按 `.gitignore` 过滤，`.git`、`node_modules` 之类自动剔除 |
| 媒体 | 只做原文件校验与保存；内容理解默认关闭，开了也要配兼容的模型。不是本地 Whisper 转写，也不是本地抽帧 |
| 云文档 | 默认只导 wiki 的入口文档 |
| 网页与整站 | 单页默认只抓入口；整站会合成一棵资源树 |

### 三种进法，外加一条 Connector

资源从哪儿来，决定了接进来要付什么代价：

- **URL**：服务端自己去抓，抓完即快照；

- **本地文件上传**：客户端先把文件传上去，换回一个临时文件号，再按这个号导入，上传的就是一份**一次性快照**；

- **Git**：先 clone，再按 `.gitignore` 过滤掉不需要的内容，所以比前两条多等一步。

Connector 是第四种进法，绕开标准流水线：

- 调用时显式声明来源类型（比如对象存储 `tos`、`git`）；

- 并且必须给出一个确定的落点路径——不能只给父目录，不能复用上传来的临时文件，也不能「提交后等它跑完」；

- 凭证跟着这一次调用走，用完即弃，不写进资源元数据。

> 取舍很简单：能用 URL 拿到就别用 Connector。它是给「标准接入够不着、但确实有对象存储或 git 凭证」的场景准备的。

### 导入参数

导入资源时的参数按作用分四组：决定落点的、决定形态的、决定收什么的，以及剩下的三个开关。

**决定落点**的参数：

| 参数 | 作用 |
|---|---|
| `to` | 覆盖：目标已存在就刷新，本次没生成的旧文件会被删掉 |
| `parent` | 追加：资源名按来源名生成，重名加 `_1`、`_2`，绝不覆盖 |

> 两者互斥，不能同时写。要定时刷新就得有一个固定目标，通常就是 `to`。

> 刷新是按内容比对的：`root_uri`（内容落在 `viking://` 下的根路径）与 `to` 相同时，没变的内容复用，只处理变化的部分。

**决定形态**的参数：

| 参数 | 取值与行为 |
|---|---|
| `processing_mode` | `semantic_and_vectors`（默认）：生成摘要（L0）与概览（L1）并向量化；`vectors_only`：只向量化，跳过摘要 |
| `parse_mode` | `default`（默认）：按标题与约 2000 字符上限切分；`no_split`：不切分，单文件且不给 `to` 时直接落在父目录，不建包目录 |
| `watch_interval` | 定期刷新的间隔，分钟数，默认 0；大于 0 时建定时任务，到期重新导入 |

> 本地文件上传得到的是静态快照，不能设 `watch_interval`，源变了只能重新导一次；URL、Git 与 Connector 都能按各自的源定期刷新。

> 定时任务到期会重新导一次，覆盖同一个 `to`；要改间隔或暂停用 `PATCH /api/v1/watches/{task_id}`，要释放目标用 `DELETE`。

> 同一目标上有多个任务时按 URI 查会返回 `409`，只能按 `task_id` 操作。这里的编号是定时任务自己的，不是某次导入返回的那个。

**决定收什么**的参数：

| 参数 | 作用 |
|---|---|
| `include` / `exclude` | 按 glob（用通配符匹配文件路径的写法）只收 / 不收哪些文件 |
| `ignore_dirs` | 目录名黑名单，逗号分隔 |
| `preserve_structure` | 目录导入时是否保留原目录层级 |
| `strict` | 严格模式：遇到不支持或解析失败的文件时，整批导入直接失败 |
| `directly_upload_media` | 媒体是否直传，默认开 |
| `source_name` | 来源显示名，本地文件默认用原文件名 |
| `tags` / `tag_mode` | `k=v` 形式的检索标签；`tag_mode` 决定写不写、替换还是追加（`replace` / `append` / `clear`） |
| `acl` | 最终导入根的直接 ACL，要 manage 权限；不传就沿用已有权限 |

**剩下的三个**参数：

| 参数 | 作用 |
|---|---|
| `reason` | 非空时把「导入原因、资源 URI」送进记忆抽取链路，删资源时能顺着 `resource_refs` 清引用；只读 reason 与目录摘要 |
| `wait` | `false` 入队即返回；`true` 等这一次导入自己的活儿做完 |
| `timeout` | 已废弃，传了也被忽略，超时在客户端配 |

> `reason` 是唯一「导入顺手写记忆」的口子，它写进 `entities` / `events` / `preferences` 这些常规类型，没有专门的「资源记忆」目录。

## 第三章：以技能形式接入

技能不是接口，也不是进程。它就是一个包——一份 `SKILL.md` 加若干附件，装进 `viking://` 之后由消费方读取。

这一章只有一件事要讲：这个包怎么进来。

### `add_skill` 只负责装

`add_skill` 是安装技能的入口。

无论走 HTTP 接口、命令行还是 agent 工具调用，背后都是同一件事：把一个包写进文件系统，并告诉你它落在哪。

### 能装什么

`add_skill` 的输入可以是四种形态，但不是四种技能类型——装完之后都是同一个东西：一份 `SKILL.md` 加附件。

| 你给什么 | 它怎么处理 |
|---|---|
| 一段 `SKILL.md` 文本 | 直接写入 |
| 结构化字典 | 按字段拼成文档 |
| 一个 MCP 工具定义 | 把工具说明翻译成技能文档 |
| 一个 Git 仓库或 GitHub 子目录 | 从仓库里取出那个目录 |

> 一个 MCP 工具定义装成技能后，只是多了一段说明书。工具能不能真的被调用，取决于它有没有被挂成节点，技能本身不提供调用能力。

> 本地文件不在这四种里：HTTP 接口不接受本机路径，服务端看不到你的磁盘；要先上传换一个临时文件号，再按这个号装。

`SKILL.md` 的 frontmatter 只有两个必填：

- `name`（不超过 64 个 ASCII 字母、数字、下划线或连字符）；

- `description`。

## 第四章：以实时上下文形式接入

前三条线都在搬内容，这一条不搬：它把一个外部工具登记成 `viking://` 下的一个节点。读这个节点，等于当场调用那个工具。

### 接入方式

**第一步，登记**：告诉 OpenViking 有一个外部 MCP 服务器，给出它的地址与名字，同时指定往哪个挂载根写。

> 挂载根有两处：`viking://agent/tools/` 是账号共享，`viking://user/<id>/tools/` 是当前用户私有、用到才创建。

**第二步，挂载**：在这个服务器的工具清单里挑一个，挂成一个节点。要给它起名、写描述，还可以预置固定参数、设超时（默认 60 秒）。

> 同一批工具可以一次挂完，也可以整批卸掉；上游工具变了，重新同步一次。

### 能被读的只有只读工具

读工具节点就是调那个工具，返回值就是工具的输出。

只有只读工具会被当成普通文件读。声明为非只读或破坏性的工具，不会被检索链路顺带触发，必须显式调用——这是一道安全边界。

### 和资源的区别

资源是**快照**，抓进来就固定了；挂载是**引用**，每次读都可能拿到最新数据。

节点本身很轻：名字、描述、预置参数，工具真正的数据留在外部服务器上。

> 但在文件系统这一层，它并不特殊：挂载写盘走的是同一条写入链路，所以工具节点同样占路径、同样有目录级 L0/L1。
