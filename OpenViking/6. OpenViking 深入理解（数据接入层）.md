# OpenViking 深入理解（数据接入层）

## 序言

> date: 2026/11/11

由大肥鱼创作，我负责校对。目的是更细致地介绍 OpenViking 的理念、架构、功能和执行流程。

目前计划从五个层次理解 OpenViking 的内部架构，这是第二节：数据接入层。

这一篇只回答一个问题：**数据怎么从外部进入 OpenViking 的文件系统**：

- 从哪个口进来、进门时被拆成什么、落在哪个 `viking://` 路径、写到哪一步算交接完成。

进来之后怎么被摘要、怎么被向量化、怎么被抽成记忆，本篇不展开。

## 总览

外部数据有四条**进入**路径：

| 入口 | 典型动作 | 落点 | 
|---|---|---|
| 对话 | DSH 里聊天，插件自动捕获并逐条写入 | `viking://user/<id>/sessions/dsh-session-<session_id>/` | 
| 资源 | 导入文件、URL、Git 仓库、云文档、整站 | `viking://resources/`、`viking://user/<id>/resources/` | 
| 技能 | 安装 `SKILL.md`、目录、zip、Git 来源 | `viking://user/<id>/skills/<name>/`、`viking://agent/skills/` | 
| 实时上下文 | 注册 MCP 服务器，把工具挂成节点 | `viking://agent/tools/`、`viking://user/<id>/tools/` |

对话、资源、技能是「搬内容」：把外面的东西拿到文件系统里存一份副本，所以是**快照**——源变了不会自动跟着变，要重新导入。

实时上下文是「登记地址」：不搬正文，只在文件系统里挂一个节点（**引用**），读的时候才去调工具。

> 所以「接入」在这里有两层意思：把东西搬进来（前三），和在文件系统里造一个入口（后一）。

> 共同点是**最后都要占一个 `viking://` 路径**。

无论走哪个口，都会经过下面四步；资源那条线四步全走，其余三条只占其中几步：

1. 内容先变成可读文本——文档类转 Markdown，本来就是文本的（对话、技能）原样收下，媒体只保留原文件；

2. 在 `viking://` 里确定一个地址，建目录树，URI 冲突自动改名；

3. 正文写进 AGFS；

4. 把「写摘要、算向量」这类任务排进队列，默认不等它跑完。

第 4 步之后发生的一切，都在「已经落盘」之后，不在本篇的范围内。

## 第一章：以会话形式接入

会话形式接入的内容主要是作为记忆上下文，但也可以通过会话上传资料和技能等上下文。

### 捕获三种消息，跳过一类内容

以 OpenViking 接入 DSH 为例。跑在 DSH 进程内的 Cordis 插件捕获三种消息：

- **用户**（用户发的内容）；

- **助手**（模型答的内容）；

- **工具结果**（工具返回的）。

工具结果捕获在 DSH 上默认开启。

> 每个会话里的消息分三类角色：user、assistant、tool。

插件跳过一类内容：DSH 或其他插件注入的上下文，例如时间注入、任务通知、召回块、profile 块。

每个 DSH 会话对应一个唯一的 `dsh-session-<session_id>` 目录，子 agent 各自独立，所以会话数量通常比人以为的多。

### 用 commit 实现归档

消息本身是**逐条即时写入**的，所以会话目录里的消息会随着对话变长。

commit 决定的不是「消息什么时候进来」，而是「这一批消息什么时候被归档、可以交给后面处理」。commit 有三个自动触发点：

- 每轮对话结束时，插件数一下还有多少内容没归档，攒够 2 万 token 就提交；

- DSH 开始压缩上下文时无条件提交——压缩会重写历史，不提交就丢了；

- 会话 teardown 时再提交一次，把这次会话剩下的消息一并归档。

commit 一旦触发，就把当前全部未归档消息写成一个 archive，交给后续的语义处理。

> 服务端另有独立的自动提交策略（`auto_commit_policy`），用更大的阈值兜底那些插件管不到的会话。

### remember 工具的特殊 commit

`remember` 工具会提交一种特殊的会话。

由于 MCP 代理每个 profile 只起一个进程，拿不到「当前是哪个会话」。

所以 `remember` 工具写的是服务端临时合成的一个短会话，与 DSH 会话不同，其目录的命名格式为 `mcp-store-<hash>`。

用户看到的是「记住了一件事」，实际发生的是「新建一个会话、塞进 1–2 条消息、提交」。

## 第二章：以资料形式接入

资料形式接入后主要作为资料上下文。

### 六族格式

支持的格式可以归成六族：

| 族 | 典型格式 | 
|---|---|
| 文档 | PDF、Markdown、HTML、Word、纯文本、EPUB | 
| 表格与幻灯片 | Excel、CSV、PowerPoint | 
| 代码与仓库 | 常见语言源码、`git://`、本地目录、zip、GitHub / GitLab / Bitbucket 仓库地址、平台上的 raw 文件地址 | 
| 媒体 | 图片、音视频 | 
| 云文档 | 飞书 doc / docx / wiki / sheets / bitable / mindnote、Drive 文件与目录集合 |
| 网页与整站 | 单页、递归抓取、sitemap / RSS / Atom、`args.site=true` 自动发现 | 

以下是一些细节备注：

| 族 | 备注 |
|---|---|
| 文档 | PDF 可本地解析，也可走 MinerU API；HTML 转 Markdown；Word 与 EPUB 用 anydoc 抽正文、标题、表格与图片 |
| 表格与幻灯片 | 工作表与每页幻灯片都转成 Markdown |
| 代码与仓库 | clone 后按 `.gitignore` 过滤，`.git`、`node_modules` 之类自动剔除 |
| 媒体 | 只做原文件校验与保存；内容理解默认关闭，开了也要配兼容的模型。不是本地 Whisper 转写，也不是本地抽帧 |
| 云文档 | 默认只导 wiki 的入口文档 |
| 网页与整站 | 单页默认只抓入口；整站会合成一棵资源树 |

### 三种进法，外加一条 Connector

资料从哪儿来，决定了接进来要付什么代价：

- **URL**：服务端自己去抓，抓完即快照；

- **本地文件上传**：客户端先把文件传上去，换回一个临时文件号，再按这个号导入，传上去就是**一次性快照**；

- **Git**：先 clone，再按 `.gitignore` 过滤掉不需要的内容，所以比前两条多等一步；同一族还认本地目录与 zip。

Connector 绕开标准流水线的第四种进法：

- 调用时显式声明来源类型（比如对象存储 `tos`、`git`）；

- 并且必须给出一个确定的落点路径——不能只给父目录，不能复用上传来的临时文件，也不能「提交后等它跑完」。

- 凭证跟着这一次调用走，用完即弃，不写进资源元数据。

> 取舍很简单：能用 URL 拿到就别用 Connector。它是给「标准接入够不着、但确实有对象存储或 git 凭证」的场景准备的。

### 能否实现定时刷新

通过本地文件上传的方式接入，得到的都是静态快照，开不了定时刷新；源变了只能重新导一次。

而 URL、Git、Connector，都可以参照其指定的源进行定期刷新。

### 导入参数

导入资料时的参数按作用分四组：决定落点的、决定形态的、决定收什么的，以及剩下的三个开关。

**决定落点**的参数：

| 参数 | 作用 |
|---|---|
| `to` | 覆盖：目标已存在就刷新，本次没生成的旧文件会被删掉 |
| `parent` | 追加：资源名按来源名生成，重名加 `_1`、`_2`，绝不覆盖 |

> 两者互斥，不能同时写。定时刷新必须落在 `to` 上。

> 刷新是按内容比对的：`root_uri`（内容落在 `viking://` 下的根路径）与 `to` 相同时，没变的内容复用，只处理变化的部分。

**决定形态**的参数：

| 参数 | 取值与行为 |
|---|---|
| `processing_mode` | `semantic_and_vectors`（默认）：生成摘要（L0）与概览（L1）并向量化；`vectors_only`：只向量化，跳过摘要 |
| `parse_mode` | `default`：按标题与约 2000 字符上限切分；`no_split`：不切分，单文件且不给 `to` 时直接落在父目录下，不建包目录 |
| `watch_interval` | 分钟数，默认 0；大于 0 时建定时任务，到期重新导入 |

**决定收什么**

| 参数 | 作用 |
|---|---|
| `include` / `exclude` | 按 glob 只收 / 不收哪些文件 |
| `ignore_dirs` | 目录名黑名单，逗号分隔 |
| `preserve_structure` | 目录导入时是否保留原目录层级 |
| `strict` | 严格模式 |
| `directly_upload_media` | 媒体是否直传，默认开 |
| `source_name` | 来源显示名，本地文件默认用原文件名 |
| `tags` / `tag_mode` | `k=v` 形式的检索标签；`tag_mode` 决定写不写、替换还是追加（`replace` / `append` / `clear`） |
| `acl` | 最终导入根的直接 ACL，要 manage 权限；不传就沿用已有权限 |

**剩下的三个**

| 参数 | 作用 |
|---|---|
| `reason` | 非空时把「导入原因 + 资源 URI」送进常规记忆抽取链路，删资源时能顺着 `resource_refs` 清理引用 |
| `wait` | `false` 入队即返回；`true` 等这一次导入自己的活儿做完 |
| `timeout` | 已废弃，传了也被忽略，超时在客户端配 |

> `reason` 是唯一「导入顺手写记忆」的口子，它写进 `entities` / `events` / `preferences` 这些常规类型，没有专门的「资源记忆」目录。

### 两种落点：`to` 与 `parent`

- `to` 是覆盖：目标已存在就刷新，目录里本次没生成的旧文件会被删掉；

- `parent` 是追加：父目录不存在时配合 `create_parent` 自动创建。

两者互斥，不能同时写。

> 刷新是按内容比对的：`root_uri` 与 `to` 相同时，没变的内容复用，只处理变化的部分。

### 增量更新：watch 不是重新导入

- `watch_interval > 0` 才建任务，`WatchScheduler` 每 60 秒扫一次到期任务，到期就重新调一次 `add_resource`；

- 目标归属：一个原生 Watch 独占它解析出的目标（暂停时也占着）；Connector Watch 之间可以共享一个目标；

- 重导入**不会**更新、也不会复活已有 Watch。要改参数或恢复就 `PATCH /api/v1/watches/{task_id}`，要停就 `is_active: false`，要释放目标就 `DELETE`；

- 同一个目标上有多个可访问的 Watch 时，按 URI 查会返回 `409`，只能用 `task_id` 操作；

- 指向 sitemap / RSS / Atom 的 Watch 每次刷新重建目录树：新页面加进来，下线的页面自动消失；

- 上传来的快照不能 watch。

> 本实例 `GET /api/v1/watches` 返回 `tasks: []`、`total: 0`，还一条都没有；`viking://resources` 也是空的，所以这一章目前只有接口层面的证据。

## 第三章：技能与规则怎么进来

### 技能落库：一个包，不是一段文本

`add_skill` 接受四种东西：内联 `SKILL.md` 文本、结构化字典、MCP 工具定义（含 `inputSchema` 就自动转成技能文档）、Git 仓库或 GitHub 子目录地址。本地文件要先 `temp_upload`，HTTP 直接传本机路径是不行的。

- 落点：`target_uri` → 用户 `add_targets.skill_uri` → 服务端默认 → 当前用户私有根 `viking://user/<id>/skills/`；账号共享根是 `viking://agent/skills/`。技能不支持 peer 级作用域。

- 整个包默认处理：`SKILL.md` 加辅助文件都进摘要与索引；嵌套的 `SKILL.md` 只是普通附件，不会变成第二个技能。

- 批量来源用 `skills` 选目录名（空或 `["*"]` 表示全装）；`list_only=true` 只看不装。

- `SKILL.md` 的 frontmatter 只有两个必填：`name`（不超过 64 个 ASCII 字母、数字、下划线或连字符）与 `description`；权限声明写连字符的 `allowed-tools`，不是下划线。

> 装好的技能不会执行任何代码：它本身只是一段文本，会话开始时会被列进技能清单。装包只是「把文件放进文件系统」，跑不跑由消费方决定。

> 本实例 `viking://user/jrtat/skills` 为空，`viking://agent/skills` 也为空，技能这一路还没有内容。

### 规则落库：编译出来的

规则走另一条路：不是写进去的，是编译出来的。

`POST /api/v1/rules/compile` 收两样东西：`instruction`（一段约束文本，上限 64000 字符）或 `sources`（最多 16 个）。`sources` 有三种形态：

- 已有资源：`{"resource_uri": "viking://resources/standards"}`

- 新远程来源：`{"path": "https://..."}`

- 新本地上传：`{"temp_file_id": "...", "source_name": "..."}`

新来源会先走一遍资源导入，再抽约束。产物落在 `viking://user/<id>/memories/rules/<scenario>/`，每个 scenario 下有一份 `abstract.md` 加若干条规则 md。

- 接口是 202 + 后台任务，不是同步返回；模型叫 Compiler，默认用服务端 VLM，可用 `rules.compiler` 覆盖。

- 编译是一组显式操作，不是自由发挥：`NEW`、`UPDATE`、`REPLACE`、`NOOP`，以及 `PAUSE`、`RESTORE`、`ARCHIVE` 这类生命周期动作；说不清楚的会记 `UNCERTAIN` / `REJECT` 而不落盘。

- 普通会话提交**不会**触发编译——这是它和记忆抽取最大的区别。

它借用记忆的目录位置，身份却是规则——所以不出现在记忆类型表里。

> 这条接口在 0.5.0 时只有文档口径：本实例旧版的 openapi 里没有任何 `/api/v1/rules/*` 路由。0.5.4 起 `/api/v1/rules/compile` 与 `/api/v1/rules/search` 才真正上线。

> 本实例至今没调用过：`viking://user/jrtat/memories/rules` 直接 404，说明目录还没建，不是「建了但空」。

## 第四章：实时上下文怎么进来（0.5.4 新增）

谈「接入」时最容易漏掉这一类：它不落一份正文，而是把一个外部工具注册成虚拟文件系统里的节点。

### 注册与挂载

- 注册：`POST /api/v1/mcps` 登记一个 Streamable HTTP MCP Server，可指定挂载根。`GET /api/v1/mcps` 返回的 `root_uris` 有两处：`viking://agent/tools/`（账号共享）与 `viking://user/<id>/tools/`（按需创建）。

- 挂载：`POST /api/v1/mcps/mount` 把某个工具挂成一个节点，必填 `tool_uri`、`node_uri`、`title`；可选 `description`、`arguments`（预置确定参数）、`timeout_seconds`（默认 60）、`tags`、`wait`。批量版是 `/mcps/batch-mount` 与 `/mcps/batch-unmount`，`GET /mcps/mounts?mcp=<name>` 查当前挂载，`POST /api/v1/mcps/{name}/sync` 在上游工具变更后同步。

- 读：读这个节点等于透明调用对应工具。只有只读工具会被这样读；显式声明为非只读或破坏性的工具必须走 `POST /api/v1/mcps/invoke` 显式调用，不会被检索链路顺带触发。

### 和资源的区别：引用不是快照

资源是**快照**，抓进来就固定了；挂载是**引用**，每次读都可能拿到最新数据。这也是它被叫作「实时上下文」的原因。

> 但在文件系统这一层，它并不特殊：挂载写盘走的是同一条 `ContentWriteCoordinator`，所以工具节点同样占路径、同样会被目录级 L0/L1 覆盖。后面那一截属于下一篇。

本实例 `GET /api/v1/mcps` 返回 `servers: []`、`total: 0`，两个挂载根都还是空的；`GET /api/v1/mcps/mounts` 少 `mcp` 参数直接 400。所以这一路目前没有内容。

## 附录：移出本篇的内容（供下一篇参考）

以下五段原本写在本篇，讲的是「数据进来之后怎么处理」，不属于本章范围。它们原样搬到这里，正文一字未改，只把标题层级下调了一级。

### 原第四章：由会话生成记忆

#### 记忆提取

**记忆管线**相对于其他类型的上下文，在这段之前多一步：会话压缩 → 提取循环 → 记忆更新器。

- 压缩是把 `messages.jsonl` 里那堆原始消息整成可抽取的形态；

- 提取循环按**记忆类型**（profile、preferences、entities、events、cases……）逐类去问「这段对话里有没有这类信息」。

- 更新器决定新建一个 md 还是合并进已有条目。

#### case 抽取

这里有个门槛：先抽 case，只有本次真的产出了至少一个 case，才会继续生成 `trajectories` 与 `experiences`（这两类记忆比较特殊）。

原因是这两类是「任务执行」的产物：

- 轨迹（trajectory）是「这类任务怎么一步步做的」。

- 经验（experience）是「做完之后总结出什么」。

没有可复用的任务案例，就没有可提炼的对象。

### 原第五章：共用的后半程

#### 语义队列

语义队列要做的是给每个目录配一句摘要（L0）、一段概览（L1），让检索时能先看目录再决定进不进去。

- 资源、记忆、技能这三类上下文，每个目录的 `.abstract.md`（摘要）与 `.overview.md`（概览）都由语义队列逐层生成；

- 规则是另一条路，它的摘要只有 Compiler 写进去的 `abstract.md`，没有概览，也不经过语义队列；

- 会话（不是一种上下文类别，但在虚拟文件系统中有对应的目录）的摘要与概览在**归档时**直接写入，也不走语义队列。

语义队列只从下往上跑（叶子目录 → 父目录 → 根目录），因为父目录的概览是拿子目录的摘要拼出来的。子目录没摘要，父目录就没材料。

#### 生成摘要和概览

每层做的四件事，其实是「汇集材料 → 写概览 → 压成一句」：

1. 给本目录下的每个文件并发生成一句摘要——这些摘要只用于凑材料，不会存成文件；

2. 收集各子目录的 .abstract.md，这是上一层已经写好的那一句；

3. 把这些材料交给模型，写成 .overview.md，上限约 4000 字符；

4. 再从这份 overview 里提取出 .abstract.md，压到约 256 字符。

以下是两个容易误解的点：

- L0/L1 是**目录级**的附属文件（sidecar），不是每个文件一份。文件内容直接进向量，没有自己的摘要文件。

- 生成父目录摘要时只读子目录的 L0 正文，那几行 `source:、generated_by:、freshness:` 不进 prompt，所以这类元数据不会污染摘要。

父级刷新还有一道 **freshness 判断**：子目录 L0 正文没变，就不向上传播，避免上层摘要无谓地重写。

### 原补充：实时上下文也有 L0/L1，但只在目录上

- 工具节点自己没有 sidecar：`.abstract.md` / `.overview.md` 始终是目录级的，这一点工具与资源、记忆没有区别。

- 挂载写盘走的是同一条 `ContentWriteCoordinator`，所以 `viking://agent/tools/<server>/` 会像资源目录一样被语义队列补上 L0/L1。`agent/tools/` 根目录那两个文件是建库时写死的固定话术（`DirectoryDefinition`），不是模型生成的。

- 分类上有个小陷阱：`classify_uri` 的映射表只有 `memories`→memory、`resources`→resource、`skills`→skill，`tools` 不在表里，于是落到默认值 **resource**——节点因此按资源被向量化。

- 但**有向量不等于搜得到**：默认召回目录是 `viking://resources` 与用户根，`viking://agent/tools` 不在其中，`ContextType` 里也没有 tool。工具只能按路径 `ls` / `read` / `glob` 取，不会出现在 `find` / `search` 的结果里。

- 还有一层错位：被摘要、被向量化的是节点里的**工具定义**（title、description、参数、超时），而读出来的是**实时数据**。摘要回答「这工具能干什么」，不回答「这次返回了什么」。

### 原补充：编排与编译

Studio 里新出现的「编排」「编译」两页，对应 `/api/v1/compile/*` 这一族接口：

| 接口 | 用途 |
|---|---|
| `GET /api/v1/compile/capabilities` | 能不能编译、不能的原因（如 `NOT_CONFIGURED`） |
| `GET /api/v1/compile/config`、`/compile/configs` | 编译目标的配置、配置列表 |
| `POST /api/v1/compile`、`GET /compile/operations/{operation_id}` | 发起编译、查进度与产出 |
| `GET /api/v1/compile/embeddings` | 编译相关的向量信息 |

它的定位不是「往库里灌数据」，而是把已有资料与实时工具组织成一份 Agent 可直接读的上下文——所以产出不落在 `memories/`，也不参与记忆抽取。

本实例 `capabilities` 返回 `configured: false`、`configs` 为空，编译尚未启用。`viking://system/compile/example-skills/` 下那四个示例技能（日报、知识蒸馏、llm-wiki、会话报告）就是给它用的。

### 原补充：写入不是一条队列

第五章说「落盘 → 语义处理 → 向量化」，听上去像一条流水线走到底；实际是同一个队列池里按工种分开排。

本实例 `GET /api/v1/observer/system` 列出的十条队列：

| 队列 | 名字能读出的分工 |
|---|---|
| `AddResource` | 资源入库 |
| `ExternalParse` | 外部解析（docling 之类的解析服务） |
| `ContentWrite` | 正文落盘 |
| `Semantic` / `Semantic-Nodes` | 目录 L0/L1 与节点级语义 |
| `Embedding` | 向量化 |
| `SessionCommit` | 会话提交归档 |
| `Reindex` | 重建索引 |
| `UserDeletion` | 用户级删除 |
| `ExternalTask` | 外部任务 |

分池的意义：一条堵塞不会连坐另一条。入库 embedding 慢，不会挡住会话提交；解析服务挂了，也不会让已经落盘的正文写不进去。

> 不积压时这张表全是 0，看不出分工；一旦有 `Pending` 堆积，先看是哪条队列，再往回找是哪一步卡住——比笼统说「处理慢」有用得多。
