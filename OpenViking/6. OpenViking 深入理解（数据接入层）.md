# OpenViking 深入理解（数据接入层）

## 序言

> date: 2026/11/8

由大肥鱼创作，我负责校对。

目的是更细致地介绍 OpenViking 的理念、架构、功能和执行流程。

目前计划从五个层次理解 OpenViking 的内部架构，这是第二节：数据接入层。

## 总览

上一篇讲的是数据放在哪，这一篇讲数据怎么进来。

读完应该能回答三个问题：

- 一句话是怎么变成一条记忆的；

- 一份 PDF 进来要过几道关；

- 为什么「资源」和「记忆」看起来是两个系统，实际共用同一段后半程。

所有数据只有**三条**进入路径，**第四条**是**编译**出来的：

| 入口 | 典型动作 | 落点 |
|---|---|---|
| 对话 | DSH 里聊天，插件自动捕获 | `viking://user/<id>/sessions/` → 蒸馏进 `memories/` |
| 资源 | 导入文件、URL、Git 仓库 | `viking://resources/` 或 `viking://user/<id>/resources/` |
| 技能 | 安装 `SKILL.md` | `viking://user/<id>/skills/<name>/` 或 `viking://agent/skills/` |
| 规则 | 编译指令或已有资料 | `viking://user/<id>/memories/rules/` |

前三条最后都汇进同一条流水线：**解析 → 建树 → 落盘 → 语义处理 → 向量化**，差别只在前半段怎么把内容拿到手。

需要注意，**没有「直接写记忆」的接口**：除了手动改 `memories/` 下的 md 文件，任何一条记忆都要先变成一个会话提交，再从会话里抽出来。

正如在《OpenViking 深入来理解（上下文存储层）》中所见，就算调用 `remember` 工具，经由一个特殊的会话进入记忆。

## 第一刀：对话怎么进来

插件是跑在 DSH 进程内的 Cordis 插件，不是外挂钩子，所以能贴着会话的事件流走。

它捕获三种消息：**用户**、**助手**、**（默认）工具结果**。

它跳过两类内容：DSH 或其他插件**注入的上下文（时间、任务通知）**，以及**工具结果**——后者会被记录，但不触发召回，也不拼进检索文本。

写完不是立刻落库，而是攒到一个 commit。

commit 有三个触发点：待同步 token 超过阈值（插件默认 20000）、DSH 开始压缩上下文、会话 teardown。

每次 commit 归档**全部**已捕获的消息，所以一次提交里往往包含好几轮对话。

写入失败的消息进待写队列，下次会话开始时重放——这是崩溃后不丢记忆的原因。

会话映射很直接：一个 DSH 会话对应一个 `dsh-<session_id>` 目录，子 agent 各自独立，所以会话数量通常比人以为的多。

`remember` 工具是个例外。MCP 代理每个 profile 只起一个进程，拿不到「当前是哪个会话」，所以它写的是服务端临时合成的一个短会话，也就是 `mcp-store-<hash>`。

用户看到的是「记住了一件事」，实际发生的是「新建一个会话、塞进 1–2 条消息、提交、抽取」。
