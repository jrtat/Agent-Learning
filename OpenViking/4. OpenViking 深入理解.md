# OpenViking 深入理解

## 序言

> date：2026/11/8

由大肥鱼创作，我负责校对.

目的是更细致地介绍 OpenViking 的理念、架构、功能和执行流程。

本篇从五个层次理解 OpenViking 的内部架构。

## 第一层：上下文存储层

在这一层，我们以 Studio 中能看见的虚拟文件系统为切入点，理解 OpenViking 的上下文存储。

官方「上下文类型」把上下文分成四类：**Resource**、**Memory**、**Skill**、**Rule（Beta）**。

但“上下文存储层”在实现上是另一套东西：`viking://` 的作用域、作用域里固定的子目录，以及每个目录自带的摘要文件。

类型决定生命周期和由谁写入，存储结构决定权限和读取成本，两者不能互相替代。

### 第一刀：三个作用域

`viking://` 下只有三支，分别是 `user` / `agent` / `resources`，它们的关系是“谁能看见”：

#### user 子目录

`viking://user/<id>/`：只有用户自己能看。哪怕用 ADMIN 身份也不能读别人的 user 路径，只有 ROOT 可以跨用户读。

- `viking://user/` 目录中都是由以 `id`（用户 ID）命名的文件夹，正如后续章节展示的那样，这些文件夹的内部结构是类似的；

#### agent 子目录

`viking://agent/`：在账号内共享的能力与配置目录，其子目录分别如下所示：

- `skills/`: 共享技能

- `tools/`: 规划中

- `endpoints/`:　规划中

- `payments/`:　规划中

可以看出，`viking://agent/` 没有 `memories`：官方明确说明记忆不使用独立的 `memories`，记忆只放在 user 或 peer 命名空间。

#### resources 子目录

`viking://resources/`：账号共享的资料区，可以用 ACL 按目录授权。


### 第二刀：六个固定子目录

`viking://user/<id>/` 中的六个子目录是平台固定下来的，不能自己改成别的名字：

| 子目录	| 谁写入	| 装什么	| 
|---|---|---|
| memories/ |	会话提交后的抽取任务 | 九类长期记忆 |
| sessions/ | 每次对话由插件写入 |	消息流、工具结果、归档、召回日志	|
| resources/ |	你导入资料时	| 个人私有文档 |
| skills/ |	安装技能时	| SKILL.md 与配套脚本 |	
| peers/ |	启用 peer 记忆策略后	| 关于某个交互对象的记忆 |	
| privacy/ | 配置隐私类别时 | 敏感配置的分版本快照 |

最容易看漏的是 sessions 也在 user 作用域里：会话不是“另一个系统”，它本身就是一棵目录树，和记忆同源同层。

另外，peers 用来记录“关于某个交互对象”（比如某个群里的某个人）的记忆；privacy 保存敏感配置的分版本快照。

### 第三刀：memories 内部按类型分家

`viking://user/<id>/memories/` 中的六个子目录和三个子文件。

不同于`viking://user/<id>/`，官方明确记忆类型可由模板扩展或调整。

| 记忆类型	| 子目录 |	装什么 |	
|---|---|---|
| profile |	`memories/profile.md`	| 你是谁：身份、环境、习惯 |
| preferences	| `memories/preferences/` |	按主题组织的偏好 | 
| entities |	`memories/entities/` |	人、项目、工具等实体知识 |
| events |	`memories/events/年/月/日`	| 决策、里程碑、发生过什么 |
| identity | `memories/identity.md`	| 助手自己的名字、形象、自我介绍 |
| soul | `memories/soul.md`	| 助手的核心原则与边界 |
| cases	| `memories/cases/`	| 训练与评测用的任务案例 |
| trajectories |	`memories/trajectories/`	| 可复用的执行轨迹 |
| experiences	| `memories/experiences/`	| 从执行结果提炼的经验 |

有两点值得单独澄清。

**其一**，`identity.md` 与 `soul.md` 并不是关于"用户"的画像，而是助手自己的自我设定。

现在点开这两份文件，看到的还是出厂模板：

- `identity.md` 里是待填的 Name / Creature / Vibe 字段；

- `soul.md` 里是 “Be helpful, not performative” 这类原则。

也就是说，在用户的库里，“助手是什么样的”这件事还没有被定义过；这跟“记住用户”是两件事。

**其二**，`entities` 和 `events` 都再分了子目录，这也是它们看起来最“乱”的原因：

- **`entities`** 按主题（比如：人物、学术论文、工具、开源项目、教材_讲义、文档、概念、系统等，都是根据实际对话归纳的）。
  
- **`events`** 按日期 2026/11/01 … 11/08。日期那层来自路径变量 {calendar:today}，写入时由服务端渲染成具体年月日。

### 补充：session 内部

每个 sessions/dsh-xxxx/ 的结构是：
- `.meta.json`（元数据）
- `abstract.md` / `.overview.md`、`messages.jsonl`（消息流）
- `history/`（归档）
- `tools/`（有工具调用时才出现）
- `.recall_log.json`（这次会话召回了哪些上下文）。

会话结束后提交 → 触发抽取任务 → 变成 memories 里的 events / entities / preferences。

同一段对话，先以 sessions 身份存着，再蒸馏成 memories。

sessions 是原始记录，memories 是二手结论，两者都在 user 作用域里，只是生命周期不同。

### 补充：隐藏文件

每个目录都可能带有三个隐藏文件，具体如下：

| 文件名 | 内容 | 
|---|---|---|
| `.abstract.md` | L0 目录摘要，正文上限约 256 字符；检索时先读它 | 
| `.overview.md` | L1 目录概览，上限约 4000 字符；决定要不要进这个目录 | 
| `.meta.json` | 元数据，会话目录里记创建时间、来源等 | 

> `.abstract.md` 和 `.overview.md` 在各个目录中按需生成，`.meta.json` 则只在会话目录（`/sessions`）中存在。

检索时的顺序是：

- 先读 L0 判断“这个目录跟问题有没有关系”，

- 再读 L1 判断“值不值得进去”，

- 进去之后才读 L2 原文。

这就是“分层检索”在存储侧的实现方式。
